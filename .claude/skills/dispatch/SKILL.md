# Постановка задачи

Роль — из `.claude/agents/` (`brigade`, `scout`, `acceptor`, `adversary`): общие правила
уже в спеке роли, их **не повторять** — спека несёт только задачу. Запуск: Claude —
Agent tool с `subagent_type` роли; codex/отдельный терминал — по скиллу **providers**
(текст роли тогда вставляется в спеку целиком, чужой провайдер `.claude/agents/` не видит).

## Скелет спеки — порядок важен

1. **Заголовок**: веха, этап, репозиторий `E:\Unity\sharp-pico`.
2. **Что читать первым делом — поимённо.** Агент не прочтёт документ, который ему
   не назвали (PLAYBOOK §6). Минимум: раздел приказа своего этапа; роль сама читает
   PLAYBOOK §3–§4.
3. **Зона**: владеет / не трогает — таблицей, по файлам. Параллельные бригады не
   пересекаются файлами; кто в этой волне держит `dotnet` — назвать явно.
4. **Пачка**: перечень карточек, каждая с майкой (XS 1 · S 2 · M 3 · L 5 · XL 8).
   Бюджет 15–20 весов, ≤1 XL, ≤2 L, ≤2 карточки с замерами. **Крупным мазком**: зона,
   результат с числом «до», границы — а механизм выбирает исполнитель. Предписанный
   механизм — ошибка постановщика («Студия Игор»: «5 кадров по 60 мс» и «не менее 6
   картинок» оказались невыполнимы вместе; воркер выбрал сам и был прав).
5. **Решения организатора** по развилкам — закрыты заранее, с обоснованием. Рядом —
   напоминание: приказ не истина, сверять с первоисточником, расхождение в отчёт,
   не исполнять буквально (уроки M1 и M4).
6. **Границы — запретами, а не пожеланиями**, и **non-goals обязательны** («чего не
   делать» останавливает уборку от превращения в переписывание — PLAYBOOK §9). Включая
   запрет очевидного неверного хода: карточка про читаемость — упрощать игру нельзя;
   карточка про формат — двигать голдены нельзя; карточка про показ — менять правила
   нельзя. Аудитная находка в пачке — подозреваемый, а не приказ: исполнитель проверяет
   её по call sites в момент исполнения и вправе вслух отменить пункт.
7. **Прямой вопрос, ответ на который — первая строка отчёта.** Такой, на который нельзя
   ответить пересказом: «кто теперь владеет X?», «какая из двух причин у этого сида?»,
   «испортилась ли Y, когда ты сломала Z?».
8. **Чем доказывает**: числа «было → стало» на карточку; каждая новая проверка —
   с негативным контролем («сломай нарочно, покажи красное, верни»); якоря PLAYBOOK §4
   не имеют права сдвинуться. Просить **доказать, а не заявить** — все лучшие находки
   проекта пришли из таких формулировок.
9. **Формат отчёта** + раздел «Расхождения» (обязателен, даже если пуст) + «В чём
   не уверена без компиляции» (для реализационных бригад).

## Длинные спеки и хэндофф между сессиями

Спека длиннее экрана кладётся файлом (скретчпад или `docs/milestones/`) и передаётся
содержимым, не ссылкой («читай файл с планом» воркеры исполняют буквально: читают,
пересказывают и сдают пустое дерево). Для хэндоффа через границу сессии или платформы —
файл со структурой (кит SandboxWrestling, `context-handoff`): цель и критерии приёмки;
базовый коммит и зона; файлы с одной строкой «почему каждый важен»; границы и non-goals;
точные команды проверки; решения, допущения, открытые вопросы, стоп-условия.
Доказательства — один раз в этом файле, ссылками на логи, без копирования простыней.

## Чего в спеке быть не должно

- Механизма вместо результата (порядок нажатий, число кадров, имена приватных методов).
- Ссылки на файл с указанием вместо самого указания: воркеры читают план, пересказывают
  и сдают пустое дерево («Студия Игор», 3 из 4). В спеке — глагол, зона и прямое
  «работа не сделана, если своих правок нет».
- Развилок «на усмотрение» и «проверить качество» без критерия.
- Ссылок на то, чего в свежем дереве нет: диск важнее спеки.
- Двухсот строк там, где хватает двадцати: спека короткая и крупная.
