# carts/shmup — walkthrough replay

| File | What it is |
|---|---|
| `walkthrough.input` | hand-written scripted input track (grammar in its own header) |

The recorded `.qrpr` is deliberately **not** committed (work order R20: demo hashes are not
goldens until the resolution verdict); it regenerates deterministically with the command at
the bottom of this file. One convention note for every number below: a track entry `N:buttons`
is seen by the cartridge on its tick N+1 (`_ticks++` precedes `Update`), so player-side tick
numbers in this file are track-scale — one lower than the cartridge's own `Ticks`, and margins
stated as "one tick" are two on the cartridge scale.

Unlike `carts/snake/replays/golden.input` (generated by a planner that reads the running
cartridge's private fields by reflection), this track is hand-written and hand-verified: every
enemy in `carts/shmup` is stationary (see the class doc on `ShmupGame` for why), so the whole
900-tick run is arithmetic on `src/main.cs`'s own constants, not an observation. The numbers
below were re-derived from the actual source twice — once from the design, once by re-reading
`Update()`'s exact call order (`UpdatePlayerControls` → `UpdatePlayerBullets` →
`UpdateEnemyBullets` → phase branch) — and cross-checked against `Overlap()`'s exact bounding-box
test, not approximated.

## Geometry the arithmetic below depends on

At 128x72 (`ScreenWidth`/`ScreenHeight`, read in `Init`, never written as a literal):

| Quantity | Value | From |
|---|---:|---|
| HUD height | 8 px | `HudHeight` |
| field top | 8 px | `_fieldTop = HudHeight` |
| player Y (top of ship) | 62 px | `ScreenHeight - PlayerSize(8) - PlayerBottomMargin(2)` |
| player X range | 0..120 | `0 .. ScreenWidth - PlayerSize` |
| player start X | 60 | midpoint of the range |
| enemy row 0 Y | 16 px | `_fieldTop + EnemyRowGap(8)` |
| enemy row 1 Y | 26 px | row 0 + `EnemyRowSpacing(10)` |
| wave 0/2 columns (4 wide) | 39, 53, 67, 81 | `SpawnWave`, `EnemyColSpacing(14)`, centered |
| wave 1 columns (3 wide) | 46, 60, 74 | same formula, `cols=3` |

## Wave timeline (independent of player action — a wave's clock is a fixed duration, not a
kill quota, so this table holds for *any* input, including no input at all)

| Event | Tick | From |
|---|---:|---|
| wave 0 intermission ends, wave 0 active | 90 | `IntermissionTicks` (90 decrements from `Init`) |
| wave 0 active ends, wave 1 intermission starts | 290 | `90 + WaveDurationTicks(200)` |
| wave 1 active starts | 380 | `290 + 90` |
| wave 1 active ends, wave 2 intermission starts | 580 | `380 + 200` |
| **wave 2 active starts** (`_waveStartTick` = 670) | **670** | `580 + 90` |
| wave 2 active ends → last wave → **Win** | 870 | `670 + 200` |

## Wave 0: fully shot down, and never fires back

Enemies are shootable through their intermission too (`UpdatePlayerBullets` runs in both
phases) — the walkthrough uses this to clear wave 0 before it can return fire. A player
bullet fired at tick `T` from column X first satisfies `Overlap` against a row-0 enemy
(`ay < 24 && ay > 12`, bullet spawns at `ay = playerY = 62` and moves `-2`/tick **starting the
same tick it is fired**, because `UpdatePlayerBullets` runs right after the fire check in
`Update`) at `T + 19`:

| Column | Fired (tick) | Dies (tick, `fired+19`) | That enemy's own first-shot tick (`110 + 3*index`) |
|---|---:|---:|---:|
| 0 (X=39) | 25 | 44 | 110 |
| 1 (X=53) | 47 | 66 | 113 |
| 2 (X=67) | 72 | 91 | 116 |
| 3 (X=81) | 97 | 116 | 119 |

Every column dies strictly before its own scheduled shot (closest margin: column 3, one tick).
**All four of wave 0's enemies are destroyed, and none of them ever fires — the ship takes zero
damage in the entire wave.** This is the "≥1 wave shot down" the work order asks for.

## The load tick: ≥8 bullets, ≥4 enemies, tick 711

Wave 2 spawns 8 enemies (4x2) at tick 580 and goes active at tick 670 (`_waveStartTick`).
`UpdateIntermission` schedules enemy `i`'s first shot, row-major spawn order, at
`670 + FirstShotDelayTicks(20) + i * FireStaggerTicks(3)` — pure arithmetic, no RNG:

| i | column X | row | fires at tick |
|---:|---:|---:|---:|
| 0 | 39 | 0 | 690 |
| 1 | 53 | 0 | 693 |
| 2 | 67 | 0 | 696 |
| 3 | 81 | 0 | 699 |
| 4 | 39 | 1 | 702 |
| 5 | 53 | 1 | 705 |
| 6 | 67 | 1 | 708 |
| **7** | **81** | **1** | **711** |

The walkthrough fires no shot after tick 97 (see `walkthrough.input`), so none of wave 2's
enemies are touched: **all 8 are alive at tick 711.** By tick 711 the oldest bullet (enemy 0,
fired 690) has travelled `711-690 = 21` of its way toward the bottom of the screen at
`EnemyBulletSpeed = 1` px/tick — nowhere near the ~48-tick lifetime (`ScreenHeight(72) -
spawnY(24)`) that would let it leave the screen, and nowhere near hitting the player (see
below, earliest possible arrival is tick 725). **So at tick 711 all 8 of the opening volley's
bullets are alive too.** Tick 711 is the answer to "name a tick with ≥8 bullets and ≥4 enemies
alive simultaneously" — it clears the bar with exactly 8 and 8, both from enemies alone (0
player bullets are alive at that point; the last one, fired tick 97, resolved by tick 116).

## The dodge: why the ship survives wave 2 unhurt too

Enemy-bullet `Overlap` against the player (`ebY < 70 && ebY > 58`, and the bullet does **not**
move on its own spawn tick, because `UpdateEnemyBullets` already ran earlier in the same
`Update()` before `UpdateEnemyFiring` creates it) first triggers `35` ticks after a row-0 spawn
(`spawnY=24`) and `25` ticks after a row-1 spawn (`spawnY=34`):

| Column | Row 0 arrival (`fired+35`) | Row 1 arrival (`fired+25`) |
|---|---:|---:|
| 0 (X=39) | 725 | 727 |
| 1 (X=53) | 728 | 730 |
| 2 (X=67) | 731 | 733 |
| 3 (X=81) | 734 | 736 |

The ship sits at X=81 (column 3) since tick 93 — the only column whose bullets could ever hit
it there. The walkthrough starts moving right at tick 712 (one tick after the load tick) and
holds for 19 ticks, reaching X=100 at tick 730 — 4 ticks before column 3's first possible
arrival (734). X=100 is permanently safe from every wave-2 column: the widest any bullet's
hitbox reaches is column 3's `81 + 3 + 2 = 86`, well short of 100. **The ship never loses a
life in the whole 900-tick run — 3 lives spent, 0 — and the run ends in a win at tick 870.**

This last claim (win vs. game-over) is arithmetic, not an observation: `quarp sim`/`quarp
replay` print frame and audio hashes only, never the cartridge's internal `RunState`, and
`System.Console` is banned in cartridge code (`Quarp.Analyzers.BannedSurface`), so there is no
way to print it from inside the cart either.

## Dodge-window figure (work order Р7)

`EnemyBulletSpeed = 1` px/tick is the only enemy bullet speed in this cartridge. Using the same
`Overlap`-exact arrival numbers as above, the ticks from a bullet's spawn to the first tick it
could touch the ship are:

- row 1 (closer to the player, `enemyY=26`): **25 ticks** (≈0.42 s) — the binding number: the
  ship's shortest reaction budget against any bullet this cartridge fires.
- row 0 (`enemyY=16`, closer to "the edge of the screen"): **35 ticks** (≈0.58 s).

Formula: `ticks = (playerY - EnemyBulletH) - enemySpawnY + 1`, `enemySpawnY = enemyY + EnemySize`,
at `EnemyBulletSpeed = 1` px/tick (for a different speed, divide by it).

Walkthrough vs. idle at the same length (900 ticks): both hashes differ, frame and audio — the
scripted input is not a no-op, and the sfx path audibly fires (idle plays music only).
Idle 600 audio vs. the 600-tick silence digest: differs — the cart is not mute. The two
comparisons are deliberately same-length pairs: the audio digest is cumulative, so digests of
*different* lengths always differ and comparing them would prove nothing (see the
SILENT_AUDIO_* comment in `.github/workflows/ci.yml` for the general rule; the first edition
of this file compared 900 against 600 and was caught by the stage-3 adversarial review).
Recorded with:

```
quarp replay record carts/shmup -o carts/shmup/replays/walkthrough.qrpr --ticks 900 \
    --input-file carts/shmup/replays/walkthrough.input --every 20
quarp replay play carts/shmup/replays/walkthrough.qrpr --cart carts/shmup
```
