# carts/shmup — walkthrough replay

| File | What it is |
|---|---|
| `walkthrough.input` | hand-written scripted input track, 900 ticks, ends in a win |

The recorded `.qrpr` is deliberately **not** committed (work order Р20: demo hashes are not
goldens); it regenerates deterministically with the command at the bottom of this file. One
convention note for every number below: a track entry `N:buttons` is seen by the cartridge on
its tick N+1 (`Ticks` is incremented before `Update`), so **every tick quoted in this file is
cartridge-scale** — one higher than the entry that caused it.

Unlike `carts/snake/replays/golden.input` (generated by a planner that reads the running
cartridge's private fields by reflection), this track is hand-written and hand-verified: every
enemy in `carts/shmup` is stationary (see the class doc on `ShmupGame` for why), so the whole
900-tick run is arithmetic on `src/main.cs`'s own constants, cross-checked against `Overlap()`'s
exact bounding-box test and against `Update()`'s call order (`UpdatePlayerControls` →
`UpdatePlayerBullets` → `UpdateEnemyBullets` → phase branch). Where that arithmetic could be
turned into something the frame hash can see, it was — see "What was observed" below.

## Geometry, and what the move to 160×90 did to it (ADR-021, Р25)

Nothing in `src/main.cs` changed. `Init` reads `ScreenWidth`/`ScreenHeight` and the whole
formation moves; the wave clock, which is pure time, does not move at all.

| Quantity | From | 160×90 | 128×72 (history) |
|---|---|---:|---:|
| HUD height / field top | `HudHeight` | 8 px | 8 px |
| player Y (top of ship) | `ScreenHeight − PlayerSize(8) − PlayerBottomMargin(2)` | **80** | 62 |
| player X range | `0 .. ScreenWidth − PlayerSize` | 0…152 | 0…120 |
| player start X | midpoint of the range | **76** | 60 |
| enemy row 0 / row 1 Y | `_fieldTop + EnemyRowGap(8)`, `+ EnemyRowSpacing(10)` | 16 / 26 | 16 / 26 |
| wave 0/2 columns (4 wide) | `SpawnWave`, `EnemyColSpacing(14)`, centred | **55, 69, 83, 97** | 39, 53, 67, 81 |
| wave 1 columns (3 wide) | same formula, `cols = 3` | **62, 76, 90** | 46, 60, 74 |
| player bullet: fired → row 0 hit | `PlayerBulletSpeed` = 2 px/tick up from `playerY` | **+28 ticks** | +19 ticks |
| enemy bullet: fired → reaches the ship's row | `(playerY − EnemyBulletH) − spawnY + 1` at 1 px/tick | row 0 **+53**, row 1 **+43** | +35, +25 |

The last two rows are why the stage-3 track had to be replanned rather than shifted. The
formation sits at the same height and the ship dropped 18 px, so a player bullet now needs 28
ticks to reach row 0 instead of 19 — and the old "drift, pause, shoot" pacing fired its last
shot on tick 98, which reaches row 0 on tick 126, **seven ticks after** that enemy's own
scheduled shot at 119. The new schedule fires the instant the ship arrives under each column
and has no idle ticks in between.

This is not a hypothetical, and it is the reason this file was rewritten at all: replay the
stage-3 track unchanged on 160×90 and it still runs, still ends at tick 870, and still prints
a frame hash different from the idle run — it passes every Р20 check while no longer doing
what it says. What gives it away is the empty-field window (see "What was observed" below):
the replanned track goes quiet at tick 96 and stays quiet for 194 ticks, the stage-3 track only
goes quiet at tick **217** and only for 73. Those 121 ticks are the fourth enemy firing at 119,
its bullet reaching the ship at 172 (`119 + 53`), and the 45-tick invulnerability blink running
out at 217. A demo whose walkthrough silently stops being a walkthrough is exactly the failure
the work order's oracle predicted for this cart.

The same 18 px is a gift on the other side of the field: the shortest reaction budget against
any bullet this cartridge fires (a row-1 enemy, the closest one) went from **25 ticks to 43**
(0.42 s → 0.72 s at 60 Hz). That is this cart's Р7 dodge-window figure; the canonical Р7 set
lives in `docs/milestones/M4-MEASUREMENTS.md` and is not duplicated here.

## Wave timeline — unchanged by the move

A wave's clock is a fixed duration, not a kill quota, so this table holds for *any* input,
including no input at all, and it reads the same on both screens.

| Event | Tick | From |
|---|---:|---|
| wave 0 intermission ends, wave 0 active | 90 | `IntermissionTicks` (90 decrements from `Init`) |
| wave 0 active ends, wave 1 intermission starts | 290 | `90 + WaveDurationTicks(200)` |
| wave 1 active starts | 380 | `290 + 90` |
| wave 1 active ends, wave 2 intermission starts | 580 | `380 + 200` |
| **wave 2 active starts** (`_waveStartTick` = 670) | **670** | `580 + 90` |
| wave 2 active ends → last wave → **Win** | **870** | `670 + 200` |

## Wave 0: fully shot down, and never fires back

Enemies are shootable through their intermission too (`UpdatePlayerBullets` runs in both
phases), and the walkthrough uses this to clear wave 0 before it can return fire. A bullet
fired at tick `T` from a column-aligned ship first satisfies `Overlap` against a row-0 enemy
(`ay < 24 && ay > 12`; the bullet spawns at `ay = playerY = 80` and moves −2 **on the tick it
is fired**, because `UpdatePlayerBullets` runs right after the fire check) at `T + 28`:

| Column | Ship arrives (tick) | Fired (tick) | Dies (tick, `fired+28`) | That enemy's own first shot (`110 + 3·index`) | Margin |
|---|---:|---:|---:|---:|---:|
| 0 (X=55) | 22 | 23 | 51 | 110 | 59 |
| 1 (X=69) | 37 | 38 | 66 | 113 | 47 |
| 2 (X=83) | 52 | 53 | 81 | 116 | 35 |
| 3 (X=97) | 67 | 68 | 96 | 119 | 23 |

Every column dies well before its own scheduled shot — the tightest margin is 23 ticks, where
the stage-3 track on 128×72 had one. **All four of wave 0's enemies are destroyed, none of them
ever fires, and the ship takes zero damage in the entire wave.** This is the "≥1 wave shot
down" the work order asks for.

## The load tick: ≥8 bullets, ≥4 enemies, tick 711

Wave 2 spawns 8 enemies (4×2) at tick 580 and goes active at tick 670 (`_waveStartTick`).
`UpdateIntermission` schedules enemy `i`'s first shot, row-major spawn order, at
`670 + FirstShotDelayTicks(20) + i · FireStaggerTicks(3)` — pure arithmetic, no RNG:

| i | column X | row | fires at tick |
|---:|---:|---:|---:|
| 0 | 55 | 0 | 690 |
| 1 | 69 | 0 | 693 |
| 2 | 83 | 0 | 696 |
| 3 | 97 | 0 | 699 |
| 4 | 55 | 1 | 702 |
| 5 | 69 | 1 | 705 |
| 6 | 83 | 1 | 708 |
| **7** | **97** | **1** | **711** |

The walkthrough fires no shot after tick 68, so none of wave 2's enemies is touched: **all 8
are alive at tick 711.** By tick 711 the oldest bullet (enemy 0, fired at 690) has fallen to
`y = 24 + 21 = 45` — an enemy bullet is retired at `y ≥ ScreenHeight`, i.e. at y = 90, so it is
nowhere near expiring, and it is not going to be absorbed by the ship either (see the dodge
below). **So at tick 711 all 8 of the opening volley's bullets are alive too.** Tick 711 is the
answer to "name a tick with ≥8 bullets and ≥4 enemies alive simultaneously" — it clears the bar
with exactly 8 and 8, both from enemies alone (0 player bullets are alive at that point; the
last one, fired at tick 68, resolved at tick 96).

## The dodge: why the ship survives wave 2 unhurt too

Enemy-bullet `Overlap` against the player (`ebY < 88 && ebY + 4 > 80`; a bullet does **not**
move on its own spawn tick, because `UpdateEnemyBullets` already ran earlier in the same
`Update()` before `UpdateEnemyFiring` creates it) first triggers 53 ticks after a row-0 spawn
(`spawnY = 24`) and 43 ticks after a row-1 spawn (`spawnY = 34`):

| Column | Row 0 arrival (`fired+53`) | Row 1 arrival (`fired+43`) |
|---|---:|---:|
| 0 (X=55) | 743 | 745 |
| 1 (X=69) | 746 | 748 |
| 2 (X=83) | 749 | 751 |
| 3 (X=97) | **752** | **754** |

A bullet is drawn 2 px wide at `enemyX + 3`, so column 3's bullets occupy x ∈ [100, 102) and
the ship's box at X=97 is [97, 105) — they overlap, and column 3 is the only column that can
reach the ship where it has been parked since tick 67. The walkthrough starts moving right at
tick 712 (one tick after the load tick) and holds for 19 ticks, reaching X=116 at tick 730 —
22 ticks before column 3's first possible arrival. X=116 is permanently safe from every wave-2
column: the widest any bullet's hitbox reaches is 102, well short of 116, so the later volleys
cannot touch the ship however their `RndInt` jitter falls. **The ship never loses a life in the
whole 900-tick run — 3 lives spent, 0 — and the run ends in a win at tick 870.**

Wave 1 needs no dodge at all: its bullets sit at x = 65/79/93 and the ship's box is [97, 105),
so the formation cannot reach the ship where the wave-0 sweep left it, for any jitter.

## What was observed, and what stayed arithmetic

`quarp sim`/`quarp replay` print frame and audio hashes only, never the cartridge's internal
`RunState`, and `System.Console` is banned in cartridge code (`Quarp.Analyzers.BannedSurface`),
so lives and wave state cannot be printed from inside the cart. Three of the claims above were
nevertheless turned into things the frame hash can see, with `--every 1`:

1. **Wave 0 cleared, at tick 96.** With the field empty, the pool empty and the ship still, the
   frame has nothing left that animates: `--every 1` shows one unbroken run of identical hashes
   from tick **96 to tick 289**, 194 ticks long, ending exactly when wave 1 spawns. A single
   surviving enemy would have bobbed (`DrawEnemy`'s `Ticks/8` wobble) and broken the run; a
   surviving *column* would have shot at the ship. This also re-derives the column positions:
   four shots fired from x = 55/69/83/97 all connected, which they could not have done if the
   formation were anywhere else.
2. **The run ends at tick 870, and not earlier.** After `EndRun` the simulation stops moving
   (bullets freeze, `Update` returns early) and the frame becomes a pure function of `Ticks`:
   the enemy bob has period 32 and the "PRESS START" blink period 40, so the whole picture
   repeats every 160 ticks. Over a 1100-tick recording the earliest tick T for which
   `hash(t) == hash(t+160)` holds for all `t ≥ T` is exactly **870** — the wave-2 clock
   expiring, i.e. the win. A game over would have ended the run on an arrival tick instead.
3. **The dodge is what keeps the third life.** Control run: the same track with the dodge
   delayed to ticks 761–779, so the ship is still in column 3 when its bullets arrive and still
   reaches X=116 by tick 780. From tick 780 on, the two runs have the same ship position, the
   same score, the same empty bullet pool and the same RNG stream — and their frames differ on
   **every one of the ticks 780…1100**. The only thing left that can differ is the `LIVES`
   readout: the control took a hit, the walkthrough did not.

What stayed arithmetic: the exact contents of tick 711 (8 bullets, 8 enemies) and the
win-versus-game-over label on the end panel. Both follow from the table above with no RNG in
the path, and observation 3 corroborates the two ingredients they rest on — the first-volley
schedule and the +53 arrival — by making a bullet from that same volley land.

One honest correction to the stage-3 edition of this file, found by running the control: the
dodge is **not** what saves the run. A variant with no dodge at all also reaches its terminal
state at tick 870 — the ship is hit once or twice out of three lives and still survives the
clock. The dodge protects lives and the "zero damage" claim, not the ending.

## Hashes

Windows-x64, this machine. Not pinned as a CI golden — Р20 keeps this a "plays through"
proof, not a golden.

| Run | Frame hash | Audio hash |
|---|---|---|
| idle, 600 ticks (`quarp sim carts/shmup --ticks 600`) | `23183ebc2ab8586f` | `32c3aa92fe723048` |
| idle, 900 ticks (`quarp sim carts/shmup --ticks 900`) | `0f91df09762bbc59` | `ec35e6e5fe1b4f02` |
| walkthrough, 900 ticks (this replay) | `0b373c49ea7d56d3` | `2178dd539eb6d1d0` |
| silence digest, 600 ticks (`quarp audio silence --ticks 600`) | — | `54738d7161a01b25` |

Walkthrough vs. idle at the same length (900 ticks): both hashes differ, frame and audio — the
scripted input is not a no-op, and the sfx path audibly fires (idle plays music only). Idle 600
audio vs. the 600-tick silence digest: differs — the cart is not mute. The two comparisons are
deliberately same-length pairs: the audio digest is cumulative, so digests of *different*
lengths always differ and comparing them would prove nothing (see the SILENT_AUDIO_* comment in
`.github/workflows/ci.yml` for the general rule; the first edition of this file compared 900
against 600 and was caught by the stage-3 adversarial review).

Unlike the dialogue cart, this one's **idle audio did change with the screen** (was
`9d18e65f8e358059` at 600 ticks on 128×72). Nothing about the audio pipeline changed; the
gameplay under it did. An idle ship is parked at the middle of the range — X=76 now, X=60
before — and on both screens that is inside wave 1's fire lane (bullets at 65/79/93 against a
ship box of [76, 84); 49/63/77 against [60, 68) before), so the idle run takes hits, and a hit
plays `SfxBoom`. Move the ship's start and the booms move with it. That last step is
arithmetic, not observation: a hit in the middle of a moving field leaves no signature a frame
hash can be read for.

Negative control for "the walkthrough differs from idle": an empty track recorded at 900 ticks
reproduces the idle hashes bit for bit (`0f91df09762bbc59` / `ec35e6e5fe1b4f02`), so the
difference is carried by the input and not by the recording.

Recorded/played with:

```
quarp replay record carts/shmup -o /tmp/walkthrough.qrpr --ticks 900 \
    --input-file carts/shmup/replays/walkthrough.input --every 20
quarp replay play /tmp/walkthrough.qrpr --cart carts/shmup
```
