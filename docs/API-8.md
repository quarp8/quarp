# Справочник API: Профиль 8

**Статус: РАТИФИЦИРОВАН (2026-08-19, вместе со SPEC-8 — ADR-024).** Поверхность
перманентна: сигнатуры не меняются, вызовы не удаляются; новые вызовы добавляются
только через ADR (прецедент — ADR-020). Ратифицировано железо: `IConsoleApi`,
protected-зеркала `Cartridge`, свойство `Q`, типы `Fix`/`SMath`/`Button`/`Font` —
включая обе перегрузки `Print` и метрики `Font.Large` (5×7; рисунок глифов — качество
реализации, не спека, правится без ADR). **Библиотека `Quarp.Api.Std` — не железо**:
растёт после релиза свободно, без ADR (SPEC-8 §8, Р31).

Источник истины по сигнатурам — `src/Quarp.Api/IConsoleApi.cs`. Картридж наследует
`Cartridge` и получает всю поверхность как protected-методы, поэтому код читается как
PICO-8 — `Cls(1); Spr(1, x, y);` — и все примеры ниже написаны так же, без префиксов.
Формат картриджа — SPEC-8 §6; правила детерминизма — SPEC-8 §7 (краткий свод — §11 ниже);
что проверяется при сборке картриджа — §12.

## 0. Вся поверхность одним экраном

## 1. Общие правила

Действуют для каждого вызова, если у конкретного вызова не сказано иное.

1. **API никогда не кидает исключений за «плохую геометрию».** Рисование за границами
   экрана мягко обрезается; чтение вне границ возвращает 0/`false`; запись вне границ —
   no-op. Картридж не обязан ничего проверять перед вызовом.
2. **Отрицательный или нулевой размер — no-op**: `width`/`height`/`cellsWide`/`cellsHigh`
   ≤ 0 и `radius` < 0 просто ничего не рисуют.
3. **Индексы вне диапазона — «пусто», не ошибка**: игрок вне 0–1 → `false`; слот `Dget`
   вне 0–63 → 0; тайл вне карты → 0. У каждого вызова расписано.
4. **Цвета маскируются** по младшим битам, а не отбрасываются: рисующие вызовы берут
   **слот видимой палитры 0–15** и маскируют аргумент `& 15` (`Cls(19)` = `Cls(3)`);
   `Pal` берёт мастер-цвет и маскирует `& 31`. Цвет в вызове рисования — всегда слот,
   мастер-цвета 16–31 доступны только через `Pal` (SPEC-8 §2).
5. **Порядок трансформаций рисования**: экранная позиция = переданные координаты −
   смещение `Camera`; затем — отсечение по прямоугольнику `Clip`. Клип задаётся
   в экранных координатах и камерой **не** смещается.
6. **Координаты и радиусы зажимаются в [−32768; +32768]** перед растеризацией
   (тот же диапазон, что у `Fix`). `Line(0, 0, 2000000000, 5, 7)` не подвесит кадр
   на секунды: конец отрезка сначала прижимается к границе диапазона, потом рисуется.
   Зажим детерминирован и одинаков на любой машине; на честную геометрию (экран
   160×90, разумный оверскан) он не влияет вообще.
7. **Исключения, которые картридж всё же может получить**: деление `Fix` на ноль
   (включая `Fix.Ratio(n, 0)`) и вызов API из конструктора картриджа (до подключения
   к консоли). Оба — честные ошибки логики: оболочка ставит паузу и показывает
   стектрейс с номером строки.

Система координат: (0, 0) — левый верхний угол, x вправо, y вниз, экран **160×90**
(SPEC-8 §1, ADR-021). Все координаты и размеры — `int`; дробные позиции храните в `Fix`
и приводите `(int)` в момент отрисовки. Размеры экрана читаются из API —
`ScreenWidth`/`ScreenHeight` (§3); числа 160 и 90 в коде картриджа писать не нужно.

**Framebuffer хранит мастер-индексы 0–31** (SPEC-8 §1): в буфер попадает уже результат
`Pal`-ремапа, а не слот. Практическое следствие ровно одно — см. `Pget`.

Состояние рисования (`Camera`, `Clip`, `Pal`, `Palt`) живёт в консоли и между кадрами
**не сбрасывается**: выставили — работает, пока не смените (или сбрасывайте сами
в начале `Draw`).

## 2. Жизненный цикл картриджа

```csharp
public class MyGame : Cartridge
{
    public override void Init()   { }   // «тик 0», часть симуляции
    public override void Update() { }   // ровно 60 раз в игровую секунду
    public override void Draw()   { }   // только рисование, состояние не менять
}
```

- В картридже — **ровно один** наследник `Cartridge`; ноль или несколько — ошибка сборки.
- **Конструктор выполняется до подключения к консоли**: вызов любого метода API из
  конструктора или инициализатора поля бросает `InvalidOperationException`.
  Всё состояние инициализируйте в `Init`.
- `Init` — «тик 0», часть детерминированной симуляции; `Ticks` внутри него равен 0.
  Здесь уже доступно всё: `Mset`, `Sset`, `Srand`, `Dget`…
- `Update` — вся логика игры. Оболочка гонит фиксированные тики: при просадке FPS
  `Update` может выполниться несколько раз подряд на один показанный кадр — пропуск
  кадров разрешён, пропуск тиков нет (SPEC-8 §7).
- `Draw` — один раз на показанный кадр, и **не меняет состояние игры**. Это конвенция,
  на которой держатся реплеи и перемотка (анализатор — M2).
- Исключение из `Init`/`Update`/`Draw` не глотается: пауза, стектрейс с номерами строк
  в терминале, баннер на экране; правка кода → пересборка и рестарт (критерий M1).
- Картридж компилируется с **отладочной оптимизацией** (`OptimizationLevel.Debug`)
  и встроенным portable PDB — поэтому номера строк в стектрейсе точные, без «съеденных»
  инлайнингом кадров. Цена нулевая: картридж ≤ 64 КБ кода, а тик-бюджет съедает ядро,
  а не пользовательский код (ADR-017).

## 3. Графика

### `ScreenWidth` / `ScreenHeight`

```csharp
int ScreenWidth  { get; }
int ScreenHeight { get; }
```

Размеры экрана в пикселях. В профиле 8 это **160 и 90** (SPEC-8 §1, ADR-021).

**Это свойства, а не константы, и это принципиально.** Константа вычисляется при
компиляции картриджа и навсегда вмерзает в его IL: игра, собранная под экран 160 пикселей
шириной, продолжит раскладывать себя на 160 пикселей на любой консоли, куда её потом
загрузят, — и никто об этом не узнает, потому что ничего не упадёт, просто справа
останется поле. Свойство читается у консоли, к которой картридж подключён, в момент
чтения. Разрешение — свойство железа, а железо выбирается при запуске, а не при сборке.

Практическое следствие для автора: **числа 160 и 90 в коде картриджа писать не нужно
нигде.**

```csharp
Print("GAME OVER", (ScreenWidth - 9 * 4) / 2, ScreenHeight / 2, 7);  // по центру
RectFill(0, ScreenHeight - 8, ScreenWidth, 8, 1);                    // HUD у нижнего края
Print("BEST", ScreenWidth - 4 * 4, 1, 6);                            // прижато вправо
if (x > ScreenWidth || y > ScreenHeight) Despawn();                  // улетело за экран
```

Правила чтения:

- **Значение постоянно на всём прогоне.** Framebuffer выделяется один раз, при создании
  консоли, и не меняет размер; читать в `Init` и запомнить в поле — законно, но незачем.
- **Читать в `Draw` — норма.** Это чтение: оно ничего не пишет в состояние симуляции,
  поэтому не нарушает правило «`Draw` не меняет состояние» (§11 п. 2) и анализатору
  `QRP1004` не интересно — ровно как `Ticks`, `Btn` или `Mget`.
- **До подключения к консоли недоступно.** В конструкторе картриджа и в инициализаторе
  поля бросается `InvalidOperationException`, как и у любого другого вызова API (§2).
  Раскладка, зависящая от размера экрана, живёт в `Init` и дальше.
- **Это не размеры листа спрайтов и не размеры карты.** Лист — всегда 128×128, карта —
  всегда 256×72 клеток (SPEC-8 §3; проверка `gfx.png` — §12); от разрешения экрана они
  не зависят и вместе с ним не менялись бы.
- `Clip()` без аргументов возвращает отсечение ко **всему** экрану, каким бы он ни был;
  прямоугольник `Clip(x, y, w, h)` пересекается с экраном (§3 `Clip`). Отдельно
  подставлять `ScreenWidth` туда не нужно.

Зачем вообще спрашивать, если в профиле 8 ответ всегда один и тот же. Во-первых, профиль
16 — другой экран, 320×180 (SPEC-16 §1, черновик; Р23 = «строгое ×2» ADR-005 × вердикт
ADR-021); это уже записанная спецификация, а не гипотеза, и код, читающий размеры,
переезжает туда без правок разметки. Во-вторых, ровно на этих двух свойствах держался
вердикт по разрешению в M4: одну и ту же собранную игру запускали на 128×72 и на запасном
160×90 (ADR-005) и сравнивали тесноту — игра, вкомпилировавшая 128, в этом сравнении
показала бы себя одинаково в обоих случаях, то есть не показала бы ничего. Вердикт вынесен
(ADR-021: 160×90, окончательно), спайк-профиль и флаг `--profile` из кода убраны, но
принцип не разовый: то же свойство несёт перенос картриджа между 720p/1080p/1440p/4K
и будущим профилем 16.

### `Cls`

```csharp
void Cls(byte color = 0);
```

Заливает **весь** экран цветом `color`: игнорирует и `Camera`, и `Clip` — клип его
не ограничивает. `Pal` при этом уважается: в буфер кладётся мастер-цвет из слота
`color & 15`, поэтому `Pal(0, 16); Cls(0);` заливает экран сумеречным, а не чернильным.

**Отличие от PICO-8:** `Cls` **не** сбрасывает ни клип, ни камеру, ни `Pal`/`Palt` —
состояние рисования переживает очистку экрана. Если начало `Draw` должно быть
«с чистого листа», сбрасывайте сами: `Clip(); Camera(); Pal(); Cls();`.

```csharp
Cls();     // залить чернильным (0) — обычное начало Draw
Cls(4);    // синий фон
```

### `Pset`

```csharp
void Pset(int x, int y, byte color);
```

Ставит один пиксель. Смещается камерой, отсекается клипом; за границами — no-op.

```csharp
Pset(80, 45, 10);   // красная точка в центре экрана
```

### `Pget`

```csharp
byte Pget(int x, int y);
```

Читает пиксель framebuffer'а. Камера применяется симметрично `Pset`; клип на чтение
не влияет; вне экрана → 0.

Возвращается **мастер-индекс 0–31**, то есть ровно то, что лежит в буфере (SPEC-8 §1),
а не слот, которым рисовали. Пока `Pal`-свопов не было, слот и мастер-индекс совпадают
и `Pget` возвращает привычные 0–15; после `Pal(7, 23)` пиксель, нарисованный слотом 7,
читается как **23**. Сравнивать результат `Pget` с номером слота можно только тогда,
когда вы точно знаете текущий ремап; надёжный способ — сравнивать с тем же мастер-цветом,
который вы клали в слот.

```csharp
if (Pget(x, y) == 0) Pset(x, y, 7);   // красить только «пустые» пиксели
```

### `Line`

```csharp
void Line(int x0, int y0, int x1, int y1, byte color);
```

Отрезок по Брезенхэму, оба конца включительно. Порядок концов не важен (форма линии
одинаковая). Выступающие за клип части обрезаются.

```csharp
Line(0, 0, 159, 89, 2);   // диагональ через весь экран
```

### `Rect`

```csharp
void Rect(int x, int y, int width, int height, byte color);
```

Контур прямоугольника толщиной 1 px. Внимание: параметры — **ширина и высота**,
а не вторая точка (не как в PICO-8). `width`/`height` ≤ 0 → no-op;
`Rect(x, y, 1, 1, c)` — один пиксель.

```csharp
Rect(0, 8, 160, 82, 1);   // рамка игрового поля под строкой HUD
```

### `RectFill`

```csharp
void RectFill(int x, int y, int width, int height, byte color);
```

Заполненный прямоугольник `width`×`height` с левым верхним углом в (x, y).
`width`/`height` ≤ 0 → no-op.

```csharp
RectFill(0, 0, 160, 8, 3);   // белая плашка HUD во всю ширину
```

### `Circ`

```csharp
void Circ(int centerX, int centerY, int radius, byte color);
```

Окружность (midpoint-алгоритм) толщиной 1 px. `radius` 0 → один пиксель в центре;
`radius` < 0 → no-op. Точная форма зафиксирована реализацией ядра и golden-master-тестами.

```csharp
Circ(80, 45, 10, 8);   // жёлтая окружность
```

### `CircFill`

```csharp
void CircFill(int centerX, int centerY, int radius, byte color);
```

Заполненный диск. Краевые случаи — как у `Circ`.

```csharp
CircFill((int)x, (int)y, 3, 10);   // «шарик» в Fix-координатах
```

### `Spr`

```csharp
void Spr(int sprite, int x, int y, int cellsWide = 1, int cellsHigh = 1,
         bool flipX = false, bool flipY = false);
```

Рисует спрайт 8×8 номер `sprite` (0–255; лист 128×128 = сетка 16×16 спрайтов,
нумерация построчно) с левым верхним углом в (x, y). `cellsWide`/`cellsHigh` собирают
«большой» объект из соседних клеток листа вправо и вниз; `flipX`/`flipY` зеркалируют
**весь собранный блок**, а не каждую клетку отдельно.

- Пиксели прозрачных цветов (по умолчанию — только цвет 0, см. `Palt`) не рисуются;
  прозрачность проверяется по **исходному** значению пикселя в листе, до `Pal`-подмены.
- Непрозрачные пиксели проходят через `Pal`: значение листа `s` рисуется как мастер-цвет
  из слота `s`.
- `sprite` вне 0–255 → no-op; блок, выходящий за правый или нижний край листа,
  обрезается по листу, без заворота на следующий ряд спрайтов.

```csharp
Spr(1, (int)x, (int)y);                 // один спрайт 8x8
Spr(4, 32, 24, 2, 2, flipX: true);      // блок 16x16 из клеток 4,5,20,21, зеркально
```

### `Map`

```csharp
void Map(int cellX, int cellY, int screenX, int screenY,
         int cellsWide, int cellsHigh, byte flagFilter = 0);
```

Рисует прямоугольный регион карты (`cellX`, `cellY`, размер в тайлах) с экранной
позиции (`screenX`, `screenY`). Каждый тайл — спрайт с тем же номером, рисуется тем же
путём, что и `Spr` (уважает `Pal`/`Palt`/`Camera`/`Clip`).

- Карта — 256×72 тайлов (SPEC-8 §3); ячейки региона за пределами карты читаются как 0.
- **Тайл 0 — «пустота», не рисуется вовсе** (как в PICO-8: спрайт 0 зарезервирован
  под «ничего»). Пустая карта поверх фона — это ноль работы и ноль пикселей, а не
  256×72 отрисованных спрайтов 0. Следствие: спрайт 0 из листа через `Map` не нарисовать
  никогда — держите в клетке 0 пустоту, а фоновый узор кладите в клетку 1 и дальше.
  На `Spr(0, ...)` правило не распространяется: он рисует спрайт 0 как обычно.
- `flagFilter` ≠ 0 → рисуются только тайлы, у которых установлены **все** биты фильтра:
  `(флаги тайла & flagFilter) == flagFilter`.
- Слой один; параллакс — повторные вызовы `Map` с разными регионами и смещениями.

```csharp
Map(0, 0, 0, 0, 20, 12);                     // экран тайлов из угла карты (20 = ScreenWidth/8;
                                              // 12 с запасом на нецелые 90/8 = 11.25 — лишнее клипуется)
Map(20, 0, 0, 8, 20, 11, flagFilter: 1);     // второй экран, только тайлы с флагом 0
```

### `Mget` / `Mset`

```csharp
byte Mget(int cellX, int cellY);
void Mset(int cellX, int cellY, byte tile);
```

Чтение и запись тайла карты. Вне карты 256×72: `Mget` → 0, `Mset` → no-op.
Изменения карты — часть состояния симуляции (делайте их в `Init`/`Update`, не в `Draw`).

```csharp
if (Mget(cx, cy) == 42) return;   // клетка занята
Mset(5, 3, 42);                   // поставить тайл 42
```

### `Fget` / `Fset`

```csharp
bool Fget(int sprite, int flag);
void Fset(int sprite, int flag, bool value);
```

Флаги спрайтов: 8 булевых флагов (индексы 0–7) на каждый из 256 спрайтов — метки вроде
«твёрдый», «шипы», «вода». `sprite` вне 0–255 или `flag` вне 0–7: `Fget` → `false`,
`Fset` → no-op. Начальные значения загружаются из `flags.bin` картриджа (нет файла — нули).

```csharp
bool solid = Fget(Mget(cx, cy), 0);   // флаг 0 = «твёрдый» тайл
```

### `Sget` / `Sset`

```csharp
byte Sget(int x, int y);
void Sset(int x, int y, byte color);
```

Чтение и запись пикселя **листа спрайтов** (координаты 0–127 по обеим осям, значения
0–15). Вне листа: `Sget` → 0, `Sset` → no-op. Открывает генеративную графику: рисуйте
спрайты кодом в `Init`, потом штампуйте их `Spr`. Лист — часть состояния симуляции.

```csharp
Sset(0, 0, 7);          // пиксель в спрайте 0
byte c = Sget(8, 0);    // левый верхний пиксель спрайта 1
```

### `Print`

```csharp
int Print(string text, int x, int y, byte color);              // мелким
int Print(string text, int x, int y, byte color, Font font);   // тем, который назвали
```

Рисует текст системным шрифтом. Шрифтов **два**, оба лежат в каждой консоли, и какой
взять — решает автор картриджа в каждом вызове. Поддерживается ASCII 32–126.

Это две перегрузки, а не один вызов с необязательным аргументом, и это не косметика:
значение аргумента по умолчанию компилятор вкладывает **в место вызова**, поэтому факт
«без шрифта — значит мелкий» размножился бы по трём сборкам сразу (интерфейс, ядро,
базовый класс картриджа) и мог бы в них разойтись. Здесь он живёт ровно в одном месте —
в реализации четырёхаргументной перегрузки, — и его сторожат якорные хэши змейки.

| Шрифт | Глиф | Ячейка (advance × межстрочье) | Колонки × строк на весь экран (160×90) |
|---|---|---|---:|
| `Font.Small` — умолчание | 3×5 | **4 × 6** | 40 × 15 |
| `Font.Large` | 4×6 | **5 × 7** | 32 × 12 |

Одна колонка вместо прежних двух — с ADR-021 профиль 8 однозначен: спайк `Profile8Wide`
(`8w`) и сравнение «128×72 против 160×90» из черновика удалены вместе с флагом
`--profile`. 12 строк крупного шрифта на весь экран — не 90/7 (нецелое 12.857), а
`ScreenHeight / 7` с отбрасыванием остатка, тот же принцип целочисленного деления, что
и у тайловой сетки (SPEC-8 §1).

Мелкий — тот же шрифт, что был у консоли всегда: вызов без пятого аргумента рисует
ровно те же пиксели, что рисовал до появления второго шрифта. Крупный стоит примерно
трети символов в строке и покупает настоящие выносные (`g j p q y` свисают под базовую
линию) и более широкие буквы — размен, который нужен прозе и не нужен HUD-у. Замер на
живом тексте — `carts/dialogue/README.md` §«Числа Р7».

**Возвращает x после последнего глифа** — `x + advance × число напечатанных символов`,
где advance равен 4 у мелкого и 5 у крупного; возвращаемое значение не зависит от камеры
и клипа (чистая функция от текста, `x` и шрифта).

- Пустая строка (и `null`) → ничего не рисует, возвращает `x`.
- `\n` — **перевод строки**: курсор возвращается к исходному `x` и опускается на
  межстрочье выбранного шрифта (6 px мелким, 7 крупным). После `\n` возвращённое
  значение — это позиция после последнего глифа **последней** строки, а не ширина
  всего текста.
- Прочие символы с кодом меньше 32 пропускаются вообще, **не сдвигая курсор**.
- Символы вне ASCII 32–126 рисуются пустой коробкой (у крупного шрифта эта коробка
  не совпадает ни с одним из 95 глифов; у мелкого она пока побитово равна цифре `0` —
  известный долг, `tasks/open/debt-fallback-zero.md`).
- Смещается камерой, отсекается клипом — как любое рисование.
- Шрифт — **аргумент вызова, а не режим**: «текущего шрифта» в консоли нет и не будет.
  Скрытый режим — это то, что один путь `Draw` забывает восстановить, и забывает он
  ровно в том кадре, о котором потом спорит реплей.
- **Игрок шрифт не выбирает** (решение владельца, 2026-08-18). Текст попадает
  в framebuffer, framebuffer хэшируется, хэш — контракт детерминизма (SPEC-8 §7):
  переключение шрифта в оболочке сдвинуло бы пиксели под всеми записанными реплеями
  и переразбило бы любую вёрстку, которая мерит себя в ячейках глифа. Размер шрифта —
  такое же решение автора картриджа, как размер спрайта. Встроенный редактор кода (M9)
  рисует в хостовом UI, вне framebuffer, и к этому запрету отношения не имеет.

```csharp
int x2 = Print("LIVES ", 2, 1, 3);
Print("<3", x2, 1, 10);                    // продолжить с конца предыдущего текста
Print("READY?", (ScreenWidth - 6 * 4) / 2, 32, 8); // центрирование: ширина = 4 * длина
Print("MARA", 21, 41, 6);                          // подпись — мелким
Print("The glass is clean,", 21, 48, 3, Font.Large); // проза — крупным, 5 px на символ
```

> Три пункта выше — про `\n`, про символы меньше 32 и про возвращаемое значение после
> `\n` — исправлены 2026-08-18 по коду (`tasks/open/bug-api8-print-doc.md`): документ
> утверждал, что переносов строк нет, а `\n` продвигает курсор на 4 px, — ядро с самого
> начала делало другое, и картриджи опирались на реальное поведение. Нормативным принято
> поведение кода (прецедент Р4.3: где спека отдаёт поведение реализации, правится спека);
> на каждый из трёх пунктов есть тест в `RasterizerPixelTests`.

### `Camera`

```csharp
void Camera(int x = 0, int y = 0);
```

Задаёт смещение камеры: всё последующее рисование сдвигается на (−x, −y) — т.е.
`Camera(10, 0)` «смотрит правее», мир уезжает влево. `Camera()` — сброс в (0, 0).
На `Clip` и `Cls` не влияет.

```csharp
Camera((int)scrollX, 0);      // мир — со смещением
Map(0, 0, 0, 0, 32, 9);
Camera();                     // HUD — в экранных координатах
```

### `Clip`

```csharp
void Clip(int x, int y, int width, int height);
void Clip();
```

Ограничивает рисование прямоугольником в **экранных** координатах (пересекается
с границами экрана; камера его не смещает). `width`/`height` ≤ 0 → пустой клип,
рисование полностью подавлено до следующего `Clip`. `Clip()` без аргументов — сброс
на весь экран.

```csharp
Clip(0, 8, 160, 82);       // рисуем только в игровом поле, HUD не задевая
CircFill(80, 8, 20, 8);
Clip();
```

### `Pal`

```csharp
void Pal(byte slot, byte color);
void Pal();
```

Перенаправляет видимый слот `slot` (0–15) на любой мастер-цвет `color` (0–31):
затемнения, ночные палитры, вспышки, «секретные» двойники (SPEC-8 §2). Действует на всё
**последующее** рисование (включая `Cls`); уже нарисованные пиксели не перекрашиваются.
`Pal()` — сброс всех слотов в тождество (слот i → мастер i). Аргументы маскируются:
`slot & 15`, `color & 31`.

```csharp
Pal(7, 23);   // зелёный слот теперь «лесной» — ночная версия
Pal();        // вернуть как было
```

### `Palt`

```csharp
void Palt(byte color, bool transparent);
void Palt();
```

Помечает цвет (0–15) прозрачным или непрозрачным для `Spr`/`Map`. По умолчанию
прозрачен только цвет 0. Прозрачность проверяется по исходному значению пикселя
в листе спрайтов, до `Pal`-подмены. `Palt()` — сброс к умолчанию.

```csharp
Palt(0, false);   // чёрный в спрайте теперь рисуется
Palt(11, true);   // прозрачным стал розовый
```

## 4. Ввод

Логические кнопки (SPEC-8 §5) — маппинг на физические устройства делает оболочка,
картридж видит только `Button`:

```csharp
public enum Button { Left = 0, Right = 1, Up = 2, Down = 3, O = 4, X = 5, Start = 6 }
```

Дефолт desktop-оболочки: P0 — стрелки, Z (O), X (X), Enter (Start), плюс геймпад 0;
P1 — геймпад 1. Мыши и текстовой клавиатуры в профиле 8 нет.

### `Btn`

```csharp
bool Btn(Button button, int player = 0);
```

Кнопка удерживается в текущем тике. `player` вне 0–1 → `false`; значение `button`
вне enum → `false`.

```csharp
if (Btn(Button.Right)) x += speed;   // удержание = движение
```

### `Btnp`

```csharp
bool Btnp(Button button, int player = 0);
```

«Нажата только что»: кнопка нажата в этом тике **и** не была нажата в прошлом.
Автоповтора нет. Краевые случаи — как у `Btn`.

```csharp
if (Btnp(Button.O)) Jump();   // одно нажатие = одно событие
```

## 5. Звук (работает с M3)

Данные звука картридж не пишет: банки приходят из `sfx.bin` и `music.bin`
([AUDIO-FORMAT.md](AUDIO-FORMAT.md)), картриджу доступны только эти два вызова.

**Оба меняют состояние симуляции** и потому запрещены в `Draw` — правило QRP1004 отвергает
такой код. Причина не формальная: `Draw` идёт по кадрам, а не по тикам, при 30 fps
выполняется вдвое реже, а при перемотке назад не выполняется вообще, — значит писк,
запущенный из `Draw`, прозвучит разное число раз в разных прогонах, и PCM-хэш, который CI
сравнивает между архитектурами, разойдётся. Место для звука — `Init` и `Update`.

### `Sfx`

```csharp
void Sfx(int id, int channel = -1);
```

Запускает эффект `id` (0–63). `channel` 0–3 занимает этот канал безусловно; `-1`
(по умолчанию) берёт **младший свободный** канал, если свободных нет — младший из тех, что
занимает музыка, а если и таких нет, вызов не делает ничего. `id` вне 0–63 (кроме `-1`,
см. ниже) и пустой слот (`length` = 0) — тоже no-op, без ошибки.

Звук слышен в блоке того самого тика, в котором вызван `Sfx`. Длину эффекта задаёт слот
(`length` × `speed` тиков), а не вызов: 4 шага на скорости 4 занимают канал 16 тиков.

**`id` = `-1` не запускает, а останавливает** (с M4, [ADR-020](DECISIONS.md)). Две формы:
`Sfx(-1, 2)` глушит канал 2, `Sfx(-1)` — все четыре сразу. Канал замолкает, кем бы он ни
был занят: голос, который вёл музыкальный секвенсор, уходит сейчас и вернётся на
следующем паттерне — ровно так же, как если бы этот канал забрал эффект. Одно правило,
а не два.

Останавливает **только** `-1`. `-2` и меньше — по-прежнему молчаливый no-op, и значение
оставлено свободным намеренно: в PICO-8 `-2` означает «отпустить звук из петли», и если
бы мы отвечали на любое отрицательное число одинаково, добавить это потом было бы
невозможно — новое поведение не отличалось бы от прежнего молчания. `channel` вне −1..3
тоже no-op.

`Sfx(-1)` — это не «выключить звук»: **музыка от него не останавливается**. Играющая
песня просто теряет свои голоса на остаток текущего паттерна и заберёт их обратно на
следующем; закончить песню может только `Music` с отрицательным номером.

```csharp
Sfx(0);        // на любой свободный канал
Sfx(1, 3);     // строго на канал 3, перебив то, что там играло
Sfx(-1, 3);    // заглушить канал 3 — например, когда отпустили кнопку выстрела
Sfx(-1);       // заглушить все четыре; песня, если играет, вернётся на след. паттерне
```

### `Music`

```csharp
void Music(int pattern = -1);
```

Запускает песню с паттерна `pattern` (0–63); отрицательный номер — включая значение по
умолчанию — останавливает музыку и глушит каналы, которыми она играла (каналы, запущенные
через `Sfx`, продолжают звучать). Номер 64 и больше — no-op.

Паттерн, который занял бы канал, уже занятый эффектом, этот голос пропускает и подхватит
его на следующем паттерне — так тема сама расступается под писк, без всякого
планировщика. Длительность паттерна — самый длинный из его активных слотов, но не меньше
32 тиков.

```csharp
Music(0);    // включить тему с паттерна 0
Music();     // остановить
```

## 6. Случайность

RNG консоли — xoshiro128\*\*, состояние — часть симуляции; при одинаковом сиде
и одинаковых входах последовательность бит-в-бит одинакова на любой машине (SPEC-8 §7).
`System.Random` в картридже запрещён и не пройдёт проверку метаданных.

### `Rnd`

```csharp
Fix Rnd(Fix max);
```

Равномерный `Fix` в диапазоне [0; max). `max` ≤ 0 → `Fix.Zero`. Каждый вызов продвигает
состояние RNG ровно на один шаг — **и вырожденный тоже**: последовательность зависит
от количества вызовов, а не от их аргументов. Правило простое и предсказуемое: у RNG
нет «бесплатных» вызовов, которые можно вставить, не сдвинув всё дальнейшее.

```csharp
Fix angle = Rnd(Fix.One);   // случайный угол в оборотах, [0; 1)
```

### `RndInt`

```csharp
int RndInt(int maxExclusive);
```

Равномерный `int` в [0; maxExclusive). `maxExclusive` ≤ 0 → 0; состояние продвигается
всегда, как у `Rnd`.

```csharp
int cell = RndInt(freeCells);   // индекс свободной клетки для яблока
```

### `Srand`

```csharp
void Srand(int seed);
```

Пересеивает RNG: `seed` разворачивается через splitmix64 в полное состояние —
любой `int` валиден, включая 0 (нулевое состояние xoshiro невозможно по построению).
До первого `Srand` состояние задаётся консолью при запуске картриджа детерминированно:
**сид по умолчанию — 0**. Никакого «случайного» стартового сида нет и не будет — часов
и энтропии у симуляции не существует; сид — вход симуляции и фиксируется реплеем.
Хотите разную игру при каждом запуске — сохраните сид сами через `Dset`.

```csharp
Srand(42);   // одинаковая последовательность на любой машине
```

## 7. Постоянная память

64 ячейки по одному `Fix` (32 бита), переживают перезапуск картриджа и консоли.
Постоянная память — **второй вход симуляции**: реплей снимает её снимок, при проигрывании
реплея `Dset` пишет в копию, не в реальные сохранения (SPEC-8 §7).

Файл `save.dat` лежит рядом с картриджем (в папке картриджа или рядом с `.quarp8`)
и устроен предельно просто: **ровно 64 × int32 little-endian, raw-значения `Fix`,
256 байт**, слот N — по смещению 4N. Ни заголовка, ни версии, ни имени картриджа —
формат ратифицирован как есть, его можно читать и писать сторонними инструментами.
Короткий или отсутствующий файл читается как нули (недостающие слоты — `Fix.Zero`).

Кто и когда пишет:

- **`quarp run` / оболочка** — при выходе и раз в секунду, если с прошлой записи
  что-то менялось (грязный флаг). Без изменений диск не трогается вообще.
- **`quarp sim`** — **не читает и не пишет `save.dat` никогда**. Headless-прогон
  стартует с 64 нулей, а его хэш framebuffer'а зависит только от картриджа, тиков
  и ввода — не от того, кто и во что играл на этой машине. Иначе golden-master-тест
  был бы не воспроизводим (SPEC-8 §7).

### `Dget`

```csharp
Fix Dget(int slot);
```

Читает ячейку 0–63; вне диапазона → `Fix.Zero`. Отсутствующий `save.dat` — все нули.

```csharp
Fix best = Dget(0);   // рекорд; 0, если сохранений ещё нет
```

### `Dset`

```csharp
void Dset(int slot, Fix value);
```

Пишет ячейку 0–63; вне диапазона → no-op. Целые тоже удобно хранить как `Fix`
(неявное преобразование из `int`).

```csharp
if (score > Dget(0)) Dset(0, score);   // рекорд переживает перезапуск
```

## 8. Время

### `Ticks`

```csharp
int Ticks { get; }
```

Число тиков с момента `Init` (сам `Init` — тик 0); 60 тиков = 1 игровая секунда.
В `Update` и `Draw` одного тика значение одинаковое. Единственные «часы», доступные
картриджу — `DateTime` запрещён. Переполнение `int` — через ~414 суток непрерывной
игры (заворачивается; считаем теоретическим).

```csharp
if (Ticks % 8 == 0) Step();          // логический шаг каждые 8 тиков
byte blink = (byte)(Ticks / 30 % 2); // мигание с периодом в секунду
```

### Управление временем (клавиши оболочки, с M2)

Оболочка умеет останавливать, замедлять и **перематывать назад** любую игру — без
единой строчки поддержки в картридже. Это прямое следствие детерминизма: назад
консоль попадает ресимуляцией лога ввода от тика 0 (ARCHITECTURE §4).

| Клавиша | Что делает |
|---|---|
| `Space` | пауза / продолжить |
| `.` | шаг на один тик вперёд (в паузе) |
| `,` | шаг на один тик назад (в паузе) |
| `[` / `]` | медленнее / быстрее по ступеням |
| `Backspace` (удержание) | перемотка назад в реальном времени |
| `Home` | в начало сессии (тик 0) |
| `F5` | сохранить реплей в `.qrpr` |
| `F8` | воспроизвести реплей |
| `Esc` | выход |

Ступени скорости: пауза, ×1/8, ×1/4, ×1/2, **×1**, ×2, ×4, ×8.

Что из этого обязан знать автор картриджа:

- **Скорость — это частота тиков, а не другая симуляция.** При ×8 оболочка отдаёт
  8 тиков за кадр, при ×1/4 — один тик раз в 4 кадра. `Ticks` растёт ровно так же,
  `Update` вызывается ровно столько же раз на игровую секунду. Замедление не делает
  движение плавнее, а ускорение — не «промотка через кадр»: считается каждый тик.
- **Этих клавиш картридж не видит.** `Btn`/`Btnp` знают только семь логических кнопок
  (§4); `Space`, `F5` и прочее до симуляции не доходят вообще, поэтому назначить
  пробел на прыжок и подраться с паузой невозможно.
- **Индикатор рисует оболочка поверх кадра, а не картридж.** `PAUSE`, `<< 0.25x`, `REC`
  живут в отдельном слое оболочки; framebuffer остаётся ровно таким, каким его нарисовал
  картридж. Иначе индикатор попадал бы в хэш кадра и ломал голден-мастер — то есть
  ровно то, ради чего вся веха и затевалась.
- **При перемотке назад `Init` выполняется заново.** Он и так «тик 0» и часть симуляции
  (§2), но об этом легко забыть: если `Init` где-то незаметно зависит от внешнего мира,
  перемотка это вскроет.
- **Во время ресимуляции `Update` идёт без `Draw`.** Правило «`Draw` не меняет
  состояние» (§11 п. 2) из конвенции превращается в требование: всё, что накопилось бы
  в `Draw`, при перемотке просто не накопится.

### Реплеи (`.qrpr`)

`F5` кладёт рядом с картриджем файл `.qrpr` — это **не видео**. Внутри лежит только то,
чего симуляция не может вычислить сама:

1. идентификатор картриджа (SHA-256 исходников и ассетов);
2. **сид RNG** — без него `Rnd` дал бы другие числа;
3. **снимок постоянной памяти** — все 64 слота `Dget` на момент начала записи, 256 байт;
4. лог нажатий по тикам, сжатый RLE.

Пункт 3 стоит отдельного абзаца, потому что он ловит самую неприятную породу «у меня
не воспроизводится». Постоянная память — **второй внешний вход симуляции** (§7): игра,
которая читает рекорд из `Dget(0)` и раздаёт по нему сложность, без снимка
воспроизведётся только у того, у кого точно такой же `save.dat`. Со снимком — у всех.

**При проигрывании реплея `Dset` пишет в копию.** Чужой реплей не может испортить ваши
сохранения, а ваш собственный реплей не перезапишет рекорд, пока вы его пересматриваете.

Полная раскладка байт, правила RLE и совместимость версий — [REPLAY-FORMAT.md](REPLAY-FORMAT.md).
Из CLI то же самое доступно без окна:

```
quarp replay record carts/snake -o golden.qrpr --ticks 600
quarp replay play golden.qrpr --cart carts/snake
```

## 9. Тип `Fix`

Единственный дробный тип, разрешённый в коде картриджа: детерминированный fixed-point
**Q16.16**. Диапазон **[−32768; +32768)**, шаг 1/65536 ≈ 0.0000153. Чистая целочисленная
арифметика — бит-в-бит одинакова на любой платформе (SPEC-8 §7).

| Член | Что это |
|---|---|
| `Fix.Zero`, `Fix.One`, `Fix.Half` | готовые константы 0, 1, 0.5 |
| `Fix.MinValue`, `Fix.MaxValue` | −32768 ровно и +32768 − 1/65536 |
| `Fix.Ratio(int num, int den)` | точная дробь: `Fix.Ratio(1, 2)` = 0.5 — **благословлённый способ записи дробных констант** (float-литералов в картридже нет) |
| `int` → `Fix` | неявное: `Fix x = 3;` |
| `(int)fix` | **пол к −∞** (арифметический сдвиг): `(int)(-Fix.Half)` = −1, не 0 |
| `+ − * /`, сравнения | обычные операторы |
| `Fix.FromRaw(int)` / `.Raw` | сырое Q16.16-значение — для таблиц и трюков |
| `.ToString()` | инвариантная культура, до 5 знаков — **только для отладки** |

Семантика краёв (**черновик до ратификации** — любой вариант обязан быть
детерминированным и записанным, SPEC-8 §7):

- **Переполнение — wrap** (unchecked, по модулю 2³²): `Fix.MaxValue + Fix.One`
  молча заворачивается в отрицательные. Детерминировано и бесплатно.
- **Деление на ноль — исключение** (`DivideByZeroException`), в том числе
  `Fix.Ratio(n, 0)`. Молчаливый ноль маскировал бы логическую ошибку.
- `Fix.Ratio` с непредставимым результатом: обрезание к нулю до шага 1/65536
  (например, 1/3 хранится как 21845/65536); результат вне диапазона — wrap.
- Умножение считается через промежуточный `long` — само не переполняется,
  но результат за пределами диапазона заворачивается.

Практическое следствие wrap'а: квадрат величины уже при |a| > ~181 выходит за диапазон —
`dx * dx + dy * dy` безопасен для экранных расстояний (максимум ~147 px по диагонали),
но не для произвольных чисел.

```csharp
Fix speed = Fix.Ratio(3, 2);   // 1.5 — так пишутся дробные константы
x += speed;
int px = (int)x;               // пол: на экран — целые пиксели
```

## 10. `SMath` (появляется в M1)

Статический класс в `Quarp.Api`; только `Fix` и `int`, без состояния. `System.Math` /
`System.MathF` в картридже запрещены и не пройдут проверку метаданных. Устройство
и точность зафиксированы в ADR-014.

**Углы — в оборотах** (turns): 1.0 = полный круг, 0.25 = четверть. Полный круг точно
представим в Q16.16 (2π не представим точно нигде), конверсий и их ошибок нет.

### Направление: математическое, не PICO-8

`SMath.Sin` — **обычный математический синус**, без экранной инверсии:

```
Sin(0) = 0    Sin(0.25) = +1    Sin(0.5) = 0    Sin(0.75) = -1
Cos(0) = +1   Cos(0.25) = 0     Cos(0.5) = -1   Cos(0.75) = 0
```

(Углы здесь записаны десятично для читаемости; в коде картриджа четверть оборота —
это `Fix.Ratio(1, 4)`: вещественных литералов в картридже нет, §12.)

PICO-8 возвращает синус с обратным знаком (`sin(0.25)` = −1) — там его «встроили»
в экранную систему координат, где y растёт вниз. Мы этого не делаем сознательно:
инверсия чинит один частный случай (сразу класть результат в экранный y) и ломает всё
остальное — тождества, `Atan2`, перенос формул из учебника и любой код, где угол
используется не для рисования. Пусть инверсию делает тот, кому она нужна, и там,
где она видна.

> **Порт с PICO-8: поменяйте знак синуса.** `sin(a)` из PICO-8 = `-SMath.Sin(a)`;
> `cos` совпадает. Если формула перенесена «как есть» и объект крутится не в ту
> сторону — вот причина.

В экранных координатах (y вниз) это значит: `x += Cos(a)*r; y += Sin(a)*r;` крутит
объект **по часовой стрелке** при росте `a`. Хотите против часовой — пишите
`y -= Sin(a)*r`.

Гарантированный инвариант: `Atan2` согласован с `Sin`/`Cos` в том же соглашении —
`Atan2(Sin(a), Cos(a))` возвращает `a`, приведённое в [0; 1) и с точностью таблиц,
поэтому «прицелился и полетел» работает без знаков-сюрпризов:

```csharp
Fix a = SMath.Atan2(targetY - y, targetX - x);
vx = SMath.Cos(a) * speed;
vy = SMath.Sin(a) * speed;   // летит точно в цель, знаки менять не нужно
```

### `SMath.Sin` / `SMath.Cos`

```csharp
Fix SMath.Sin(Fix turns);
Fix SMath.Cos(Fix turns);
```

Табличные (1024 узла на четверть круга + линейная интерполяция), выход в [−1; 1].
Измеренная максимальная ошибка 2.2e-5 — 0.003 px при вращении радиусом во весь экран
(ADR-014). Вход любой: период 1 оборот, отрицательные углы валидны (берётся дробная
часть оборота — заворот бесплатен по построению Q16.16).

```csharp
x += SMath.Cos(a) * r;   // точка на окружности радиуса r
y += SMath.Sin(a) * r;
```

### `SMath.Sqrt`

```csharp
Fix SMath.Sqrt(Fix value);
```

Целочисленный корень (Ньютон/бинарный поиск на `ulong` от `raw << 16`), результат —
пол истинного корня до шага 1/65536. `value` < 0 → `Fix.Zero` — мягкий вариант
в духе общего правила «за плохие данные не кидаем» (§1).

```csharp
Fix dist = SMath.Sqrt(dx * dx + dy * dy);   // помните про wrap при |d| > ~181
```

### `SMath.Atan2`

```csharp
Fix SMath.Atan2(Fix y, Fix x);
```

Угол вектора (x, y) в оборотах. Сведение по октантам + таблица арктангенса 256 узлов
с интерполяцией; точность ~1e-3 оборота (~0.36°). Результат — в **[0; 1)**, а не
в [−0.5; 0.5): угол всегда неотрицательный, `Atan2(0, 0)` → 0 (вырожденный вектор
не ошибка). Порядок аргументов — `(y, x)`, как везде. Соглашение по знаку — то же,
что у `Sin`/`Cos` (см. выше).

```csharp
Fix a = SMath.Atan2(targetY - y, targetX - x);   // куда лететь снаряду
```

## 11. Детерминизм — краткий свод (SPEC-8 §7)

Полные правила и обоснования — SPEC-8 §7; здесь — то, что автор картриджа обязан
держать в голове:

1. **60 тиков в секунду, всегда.** `Init` — тик 0. Логика — только в `Init`/`Update`.
2. **`Draw` не меняет состояние.** Кадры могут пропускаться — тики никогда.
3. **`float`/`double` запрещены во всём коде картриджа**, включая `Draw`.
   Только `int` и `Fix`. Ловится при сборке картриджа — тремя проходами, §12.
4. **Математика и случайность — только консольные**: `SMath`, `Rnd`/`RndInt`/`Srand`.
   `System.Math`, `System.Random`, `DateTime`, `Guid`, `Environment`, потоки, файлы,
   сеть, рефлексия — запрещены, проверка метаданных отклонит картридж со списком мест.
5. **Симуляция однопоточна — и это тоже проверяется.** Весь `System.Threading` в бане,
   поэтому **`lock` не соберётся**: оператор компилируется в обращение к
   `System.Threading.Monitor`, и картридж падает на проверке метаданных (`QRP0003`).
   Это не придирка: второй поток — это недетерминизм по определению, а блокировать
   в однопоточном тике нечего. `Task`, `Thread`, `async`/`await` — там же.
6. **Не итерируйте `Dictionary`/`HashSet` в симуляции** — порядок обхода различается
   между машинами. Массивы, `List`, отсортированные ключи.
7. **Входы симуляции — кнопки и постоянная память.** Реплей = версия картриджа + сид +
   снимок `Dget`-памяти + лог ввода; больше ничто на симуляцию влиять не должно.

Награда за дисциплину: реплеи, перемотка в обе стороны, «машина времени» при hot
reload и одинаковые пиксели на x64/ARM64 — бесплатно.

## 12. Что проверяется при сборке картриджа

Все проверки — часть сборки, а не рантайма: картридж либо запускается, либо не
собирается со списком мест. Ошибка не убивает уже работающий картридж — при hot reload
старая сборка продолжает крутиться, диагностика уходит в терминал (ARCHITECTURE §3).

### Анализатор: QRP1001–QRP1004 (с M2)

Проверки ниже (`QRP0001`–`QRP0004`) ловят нарушение на сборке — то есть уже после того,
как вы дописали функцию. `Quarp.Analyzers` ловит то же самое **пока вы печатаете**:
это обычный Roslyn-анализатор, поэтому подчёркивание появляется в VS Code и Rider
там же, где подчёркивается опечатка в имени переменной.

| Код | Уровень | Что ловит |
|---|---|---|
| `QRP1001` | **ошибка** | `float`, `double`, `decimal` — типы, литералы, `var` с выводом в них |
| `QRP1002` | **ошибка** | недетерминированная поверхность BCL: `Random`, `DateTime`, `Guid`, `Environment`, `Task`, `Thread`, `Stopwatch` и соседи |
| `QRP1003` | предупреждение | `foreach` по `Dictionary`/`HashSet` — порядок обхода различается между запусками и машинами (SPEC-8 §7 п. 6) |
| `QRP1004` | **ошибка** | вызов, меняющий состояние симуляции, из `Draw` (в том числе через хелпер, который зовут только из `Draw`): `Rnd`, `RndInt`, `Srand`, `Sset`, `Mset`, `Fset`, `Dset` и — **с M3** — `Sfx`, `Music` |

`Sfx` и `Music` попали в список в M3 вместе со звуком. Пока они были заглушками, запрещать
было нечего; теперь они пишут состояние каналов APU, PCM входит в golden-master наравне с
кадром, и писк, запущенный из `Draw`, ломает перемотку ровно так же, как её сломал бы
`Rnd` оттуда же: `Draw` идёт по кадрам, при ресимуляции не выполняется вовсе, и число
запусков звука перестаёт быть функцией от лога ввода.

Почему `QRP1003` — предупреждение, а не ошибка: перебрать словарь, чтобы **сложить**
числа или отсортировать ключи, законно и детерминировано; недетерминизм появляется
только когда от порядка обхода зависит результат симуляции. Отличить одно от другого
анализатор не может, а ошибка, которую в половине случаев приходится подавлять, быстро
приучает подавлять её всегда. Правило простое: увидели `QRP1003` — либо отсортируйте
ключи, либо перепишите на массив/`List`.

**Анализатор приезжает к вам двумя путями**, и это не дублирование ради надёжности,
а два разных момента времени:

1. **В IDE.** `quarp new` кладёт в папку картриджа `.quarp/cart.csproj` — маленький
   dev-only проект со ссылками на `Quarp.Api` и на анализатор. Открыли папку в
   VS Code или Rider — диагностики работают.
   Рядом с M4 туда же кладутся `.vscode/launch.json` и `.vscode/tasks.json`: первый
   заставляет F5 запускать картридж под отладчиком (точки останова прямо в `src/main.cs`),
   второй перед запуском прогоняет задачу `quarp-build`, чтобы ошибки C# и нарушения QRP
   попадали в панель Problems до того, как откроется окно. Подробно — [DEBUGGING.md](DEBUGGING.md).
   Ни один из этих файлов **не входит в `.quarp8`**, не считается в лимит кода, не меняет
   идентификатор картриджа и загрузчиком игнорируется: они существуют только для редактора,
   картриджем их считать нельзя.
2. **В сборке картриджа.** Те же правила прогоняются внутри `CartCompiler`, поэтому
   запрет действует и у того, кто пишет в «Блокноте», и в CI, где IDE нет по определению.

Соотношение с кодами `QRP0xxx` ниже стоит понимать так: `QRP1xxx` — это **тот же
запрет, замеченный раньше**, а `QRP0xxx` — страховка, которая смотрит на скомпилированный
IL и метаданные, где типу спрятаться уже негде. При нормальной работе автор видит только
`QRP1xxx`; всплывший `QRP0004` означает, что вещественный тип просочился мимо исходного
текста — через generic-инстанцирование или вывод компилятора.

### Бан float — три прохода

Один текстовый фильтр обмануть легко: в исходнике слова `double` может не быть вообще —
тип приезжает через `var`, через generic-инстанцирование или через вывод компилятора.
Поэтому проходов три, и последний смотрит уже на скомпилированный IL, где спрятаться
типу негде:

| # | Проход | Что ловит | Код |
|---|---|---|---|
| 1 | ключевые слова | `float`, `double`, `decimal` в исходниках | `QRP0001` |
| 2 | идентификаторы | те же типы, записанные именем: `System.Single`, `Double`, `Decimal` | `QRP0001` |
| 3 | IL и сигнатуры | всё, что просочилось мимо текста: типы полей, параметров и локальных переменных собранной DLL, вещественные константы в IL | `QRP0004` |

Отдельно ловятся **вещественные литералы** — `0.5`, `1f`, `1e3`, `.25m`
(код `QRP0002`): чаще всего автор спотыкается именно об них.

Что автор видит в терминале:

```
src/main.cs(12,17): error QRP0002: real literal '0.25' is banned in cartridge code —
    write Fix.Ratio(numerator, denominator) instead (SPEC-8 §7)
src/main.cs(30,9): error QRP0001: type 'float' is banned in cartridge code —
    use int or Fix (SPEC-8 §7)
```

Файл, строка и колонка — на месте, лечится механически: `0.25` → `Fix.Ratio(1, 4)`,
`float` → `Fix`. Отдельно стоящий код `QRP0003` — это уже не float, а запрещённый API
(`System.IO`, `System.Threading`, `Random`, `DateTime`… — §11 п. 4–5).

### `gfx.png`

Ровно **128×128** пикселей. Каждый пиксель обязан **точно** совпасть с одним из
16 видимых цветов палитры (SPEC-8 §2) — побитовое равенство RGB, никакого «ближайшего
цвета»: подбор молча испортил бы арт и спрятал ошибку экспорта. Не совпало — ошибка
сборки **с координатами пикселя и его hex-значением**.

- **Альфа 0 → индекс 0** (прозрачный цвет консоли): рисуйте в Aseprite как обычно,
  прозрачный фон приедет цветом 0.
- **Частичная альфа — ошибка**, а не «округлим до непрозрачного». Полупрозрачных
  пикселей в индексированной консоли не существует; молчаливое округление — это
  испорченный арт, замеченный через неделю.
- Нет файла — лист спрайтов из нулей, это нормально: змейка рисуется примитивами.

### Лимиты

Код ≤ 64 КБ UTF-8 **после удаления комментариев** (comment trivia через Roslyn,
переводы строк нормализованы в `\n`) — комментарии бесплатны намеренно;
файл `.quarp8` ≤ 128 КБ; ровно один наследник `Cartridge` (ноль или два — ошибка).
Полный список — SPEC-8 §6.

## 13. Рассмотрено и решено

Предсказуемые запросы сообщества — с письменным «да/нет и почему» (требование
SPEC-8 §8), чтобы после ратификации был готовый ответ.

| Вопрос | Решение | Почему (одной строкой) |
|---|---|---|
| `Print` возвращает ширину (конечный X) | **Да** | выравнивание и продолжение строки без второго прохода по тексту |
| `Sget`/`Sset` (пиксели листа спрайтов) | **Да** | лист — память консоли; генеративная графика дёшева и в духе жанра |
| `Oval` | **Нет в v1** | `Circ`/`CircFill` покрывают главное; добавить вызов можно всегда, убрать — никогда |
| `fillp` (fill-паттерны) | **Нет в v1** | дизеринг достижим спрайтами и ручными паттернами; поверхность держим крошечной |
| `Sspr` (масштаб/поворот спрайтов) | **Нет в профиле 8** | целостность пиксельной сетки; есть в профиле 16 (SPEC-8 §3) |
| Углы | **В оборотах** (1.0 = круг) | полный круг точно представим в Q16.16, 2π — нет (ADR-014) |
| Знак синуса как в PICO-8 | **Нет, синус математический** | `Sin(0.25)` = +1; инверсия чинит один случай и ломает тождества и `Atan2` — при порте меняйте знак сами (ADR-017) |
| Тайл 0 в `Map` | **Пустота, не рисуется** | пустая карта стоит ноль работы; конвенция PICO-8, автор её и ждёт (ADR-017) |
| Размеры экрана: константы или свойства | **Свойства** `ScreenWidth`/`ScreenHeight` | константа вмерзает в IL картриджа: игра перестаёт зависеть от железа, на котором идёт, и сравнение разрешений в M4 стало бы невозможным (§3) |
| Что возвращает `Pget` | **Мастер-индекс 0–31** | в буфере лежит результат `Pal`-ремапа; врать про содержимое буфера хуже, чем объяснить (ADR-017) |
| `Cls` сбрасывает клип (как в PICO-8) | **Нет** | состояние рисования живёт до явной смены — одно правило вместо исключения из него (ADR-017) |
| Координаты за пределами `int16` | **Зажимаются в ±32768** | патологический вызов не должен растеризовать миллиард пикселей и вешать кадр (ADR-017) |
| SoftFloat как тип симуляции | **Отклонён** | в 10–20 раз медленнее `Fix` при неразличимой на 160×90 точности (ADR-014) |
| Дробные константы `Fix` | **`Fix.Ratio(n, d)`** + готовые `Zero`/`Half`/`One` | float-литералов нет — нужен точный и читаемый способ записи дробей |
| `Fix`: переполнение | **Wrap** (unchecked) — черновик до ратификации | детерминирован и бесплатен; проверки в каждом операторе съели бы тик-бюджет |
| `Fix`: деление на ноль | **Исключение** — черновик до ратификации | молчаливый 0 маскирует ошибку логики; оболочка покажет строку кода |
| Перемотка назад | **Ресимуляция от тика 0**, снапшотов в v1 нет | ноль бремени сериализации для автора; цена — линейное время (ADR-006, ADR-018) |
| Формат реплея | **Бинарный `.qrpr` + RLE** | лог входов вместо снапшота состояния: 30 минут игры ≈ 21 КБ (ADR-018) |
| Замедление и ускорение | **Частота тиков, симуляция не меняется** | `Update` всегда 60 раз на игровую секунду — иначе ×2 давал бы другую игру (ADR-018) |
| Потолок догоняющих тиков | **5 за кадр** | при перегрузке игра замедляется; неограниченный догон — спираль смерти на слабом железе (ADR-018) |
| Хот-релоад по умолчанию | **«Продолжение»**, откат в «перезапуск» | вернуться в то же место игры — смысл вехи; падение или >10 с ресимуляции честнее пережить перезапуском (ADR-007, ADR-018) |
| Индикатор паузы/перемотки | **Рисует оболочка поверх кадра** | картридж не должен пачкать framebuffer до хэширования — иначе ломается голден-мастер |
| `QRP1003` (`foreach` по словарю) | **Предупреждение, не ошибка** | перебор словаря бывает и законным; ошибка, которую вечно подавляют, перестаёт работать (ADR-018) |
