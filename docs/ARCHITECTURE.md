# Архитектура

Главное правило проекта: **ядро — чистая C#-библиотека без единой зависимости от MonoGame,
ОС и часов.** Ядро умеет одно: «дай мне нажатые кнопки — получи массив пикселей и звуковые
сэмплы». Всё остальное — тонкие заменяемые оболочки. Это правило делает дешёвыми: новые
платформы, детерминизм, тесты и веб-версию.

## 1. Слои и проекты решения

```
Quarp.sln
├─ src/
│  ├─ Quarp.Api/            # То, что видит автор картриджа: Cartridge, Fix, SMath,
│  │                            # Button, поверхность Spr/Map/Btn/... Без реализации.
│  ├─ Quarp.Core/           # Виртуальная консоль: framebuffer, растеризатор, APU,
│  │                            # RNG, карта, ввод, тики, реплеи, профили железа.
│  │                            # Чистый C#. Ссылается только на Api. Ноль зависимостей.
│  ├─ Quarp.CartKit/        # Конвейер картриджей: формат .quarp8/.quarp16 (zip),
│  │                            # Roslyn-компиляция, проверка метаданных, ALC, hot reload.
│  ├─ Quarp.Shell.Desktop/  # MonoGame-оболочка: окно, масштабирование, ввод,
│  │                            # вывод звука, меню. Windows/Linux/macOS/RPi.
│  ├─ Quarp.Cli/            # `quarp new | run | build | pack | replay` — работа без GUI.
│  └─ Quarp.Analyzers/      # Roslyn-анализатор правил детерминизма (бан float,
│                               # Random/DateTime/Task, foreach по словарю). С вехи M2.
├─ carts/                       # Демо-картриджи (каждый — папка с src/ и ассетами)
├─ tests/
│  └─ Quarp.Core.Tests/     # golden-master и детерминизм-тесты
└─ docs/
```

Зависимости строго вниз: `Shell → CartKit → Core → Api`. Картридж пользователя видит
**только `Quarp.Api`**.

## 2. Ядро (Quarp.Core)

- **Профиль железа — это данные, а не код.** `ConsoleProfile` (разрешение, палитра, лимиты,
  число каналов) — один класс с двумя предустановками: `Profile8`, `Profile16`. Никаких
  `if (is16)` по всему коду.
- **Framebuffer** — `byte[]` индексов цвета. Растеризатор (`Spr`, `Map`, `Print`, фигуры)
  пишет в него. Преобразование индексов в RGB — забота оболочки.
- **APU** — синтезатор, считающий в **целочисленной арифметике** (Q-формат): PCM
  бит-идентичен на всех платформах и входит в golden-master наравне с framebuffer'ом.
  На каждый тик — блок ровно 800 сэмплов (48000 Гц / 60 тиков). Профиль 8 — моно,
  профиль 16 — стерео с панорамой на канал (ADR-013). Буферизация на стороне оболочки:
  очередь 2–3 блоков.
- **Один вход — один выход.** Публичный контракт ядра:
  `console.Tick(InputState input)` → изменённый framebuffer + буфер аудио. Никаких колбэков
  наружу, никакого чтения времени/файлов изнутри.

### Латентность звука (замер, приёмка M3)

Windows 11 x64, .NET SDK 10.0.100-rc.2, MonoGame.Framework.DesktopGL 3.8.5 (OpenAL Soft),
сборка Release, стенд гоняет настоящий `AudioOutput` на 60 Гц.

| Участок | Величина | Как получено |
|---|---|---|
| `Sfx()` → блок готов | **0 тиков** | APU рендерит блок того самого тика, в котором вызван `Sfx` |
| блок готов → отдан устройству | **< 1 мс** | тот же кадр оболочки, сразу после тиков |
| очередь устройства | **11–28 мс** (типично; 5–31 мс по всем прогонам) | 1,33–1,87 блока в очереди на момент отдачи × 16,667 мс |
| собственный буфер драйвера | **не измерен** | MonoGame его не показывает; на WASAPI shared обычно 10–20 мс |
| **итого от `Sfx()` до звука** | **≈ 20 мс измеренных + буфер драйвера** | |

Цель приказа — «не более ~50 мс» — по измеримой части выполнена с запасом; с учётом
типичного буфера драйвера итог укладывается в 30–50 мс.

Почему очередь не измеряется одним числом: сколько блока уже проиграно в момент отдачи,
не показывает ни один API MonoGame, поэтому честная величина — интервал шириной в один
блок, а не десятичная дробь. Перекрёстная проверка сходится: наблюдаемое «отдал →
устройство начало» = 40–48 мс, что равно верхней границе интервала плюс один кадр
(16,7 мс) задержки самого наблюдения (`PendingBufferCount` опрашивается раз в кадр —
чаще оболочке негде).

Приёмка перемерила независимым стендом (три прогона по 20 с, ×1, тот же `AudioOutput`):
глубина очереди 1,39 / 1,55 / 1,70 блока → ожидание 6,4–23,1 / 9,1–25,8 / 11,6–28,3 мс,
наблюдаемый старт 40,2 / 43,0 / 45,4 мс, устройство сливает 59,87–59,90 блока в секунду,
выброшено 0–1, подставлено 1–2. Модель «верхняя граница + кадр» сошлась с наблюдением
в пределах 0,5 мс во всех трёх прогонах.

Две частоты не совпадают: тики идут ровно 60 раз в секунду, устройство на этой машине
съедает 59,72–59,95 блока в секунду (47 780–47 960 Гц вместо номинальных 48 000).
Разницу гасит очередь, и цена видна в счётчиках: на свободной машине за 20 секунд на ×1
это **0 выброшенных блоков и 1 подставленный** (тот, что заполняет очередь на старте);
под параллельной сборкой Release — 10 выброшенных и 7 подставленных, то есть примерно
щелчок в секунду. Лечится только ресемплингом под часы устройства; в M3 его нет
сознательно — это отдельная фича с собственным интерполятором.

Цифры воспроизводятся: `quarp run carts/snake`, поиграть, выйти — оболочка печатает
`[quarp] audio: queue N.NN blocks at submit (...)`.

**Что слышно на разных скоростях времени.** Правило одно (`AudioQueue`): отдавать блок,
пока в очереди меньше трёх, в конце кадра добивать тишиной до двух.

| Режим | Блоков за кадр | Что слышит игрок |
|---|---|---|
| ×1 | 1 | всё; очередь гасит кадр, отработавший два тика |
| ×2 … ×8 | 2 … 8 | примерно один блок из N: верная высота, рубленый звук. Ускорить сам звук нельзя — карта играет 48 кГц, а не 384 |
| ×1/2 … ×1/8 | 1 раз в 2…8 кадров | реальные блоки, разделённые тишиной |
| пауза, шаг, краш | 0 | тишина; чип не трогают, после снятия паузы нота продолжается |
| перемотка назад | не отдаются вовсе | тишина: ресимуляция делает тысячи блоков за миллисекунды, и к тику приземления относится только последний |

## 3. Конвейер картриджа (Quarp.CartKit)

Путь от файла до работающей игры:

1. Распаковать `*.quarp8` (zip) → `manifest.json`, `src/*.cs`, ассеты (включая банки
   звука `sfx.bin` и `music.bin` — раскладка в [AUDIO-FORMAT.md](AUDIO-FORMAT.md)).
2. Проверить лимиты профиля (размер кода без comment trivia, размеры ассетов,
   точное соответствие `gfx.png` палитре).
3. Скомпилировать Roslyn'ом в память (`AllowUnsafe = false`), ссылки — стандартные
   ref-сборки + `Quarp.Api`. **Важно: список ссылок сам по себе ничего не запрещает** —
   в .NET 5+ `File`, `Reflection`, `Random`, `DateTime` публично доступны из самой
   `System.Runtime.dll`, поэтому «запрещённое не скомпилируется» — иллюзия.
4. **Проверка метаданных скомпилированной DLL** (System.Reflection.Metadata, ~150 строк):
   все TypeRef/MemberRef сверяются с allowlist. Запрещены: `System.IO.*`, `System.Net.*`,
   `System.Threading.*`, `System.Reflection.*` (кроме атрибутов),
   `System.Runtime.InteropServices.*` (отрезает DllImport), `Random`/`DateTime`/`Guid`/
   `Environment`. Нарушение — ошибка сборки картриджа со списком мест.
   Позже (не в M1): собственная урезанная ref-сборка с именем `System.Runtime`
   (публичная поверхность стрипается через Cecil) — тогда запрещённое действительно
   не компилируется и IDE не подсказывает лишнего; type identity в рантайме сохраняется
   штатным type forwarding.
5. Загрузить сборку в **collectible AssemblyLoadContext**, создать экземпляр наследника
   `Cartridge`, связать с ядром.
6. `Init()` (тик 0) → цикл `Update()`/`Draw()`.

Практика DX (то, из чего складывается ощущение «сохранил — мгновенно работает»):
- прогревочная компиляция при старте оболочки (первый вызов Roslyn в процессе — 1–3 с
  из-за JIT самого Roslyn; последующие для 64 КБ — десятки–сотни мс);
- кэш `ImmutableArray<MetadataReference>` — ссылки не перечитываются с диска;
- **embedded portable PDB** при Emit — исключения картриджа обязаны иметь номера строк;
- debounce ~100 мс на события `FileSystemWatcher` (стреляет дублями на одно сохранение);
- dev-HUD показывает судьбу выгружаемых ALC (`WeakReference` после `Unload`) — утечки
  видимы, а не гипотетичны.

**Горячая замена кода**: при изменении `src/` — компиляция в новый ALC. Два режима:

- **Перезапуск** (по умолчанию, M1): новый экземпляр, `Init()`, старый ALC выгружается.
- **Продолжение** («машина времени», M2): состояние не переносится — ядро **ресимулирует**
  записанный лог ввода на новом коде. Благодаря детерминизму игра оказывается «в том же
  месте», но с новой логикой.

Выгрузка старого ALC — best-effort (выгрузка асинхронна и может не случиться при живых
ссылках); утечка пары сборок за сессию приемлема, длинные сессии лечатся перезапуском
процесса.

## 4. Детерминизм и время

- Оболочка гонит фиксированные тики: 60/сек, аккумулятор времени, `Update` может вызываться
  0..N раз за кадр, `Draw` — один раз. Пропуск кадров разрешён, пропуск тиков — нет.
- Симуляция — только `int`/`Fix`; float/double в коде картриджа запрещены целиком
  (SPEC-8 §7, ADR-006) — поэтому и framebuffer, и PCM бит-идентичны между платформами.
  `SMath` — табличные функции на `Fix`. RNG — xoshiro128\*\* с разворачиванием сида через
  splitmix64. Полный список запретов и правило про порядок обхода коллекций — SPEC-8 §7.
- Оболочка при старте выставляет `CultureInfo.DefaultThreadCurrentCulture = Invariant` —
  системная локаль не должна влиять ни на что.
- **Реплей** = идентификатор картриджа + сид + **снимок постоянной памяти** (256 байт;
  `Dget` — второй внешний вход симуляции, без него реплей не воспроизводим) + лог
  `InputState` по тикам в RLE. При проигрывании `Dset` пишет в копию. Форматом владеет
  ядро, файл — `.qrpr`, полная спецификация раскладки — [REPLAY-FORMAT.md](REPLAY-FORMAT.md).
  Ядро при этом файлов не открывает: оно принимает и отдаёт `Stream`/`Span<byte>`,
  а диск — забота оболочки и CLI.

### Строгий аккумулятор (оболочка, M2)

`IsFixedTimeStep` MonoGame в вехе M2 выключен и заменён собственным аккумулятором.
Причина не в идеологии: встроенный фиксированный шаг догоняет отставание неограниченно,
и на слабом железе это спираль смерти — чем больше тиков он пытается наверстать, тем
сильнее отстаёт. Наш аккумулятор копит реальное время, отдаёт целые тики и **делает
не более 5 догоняющих тиков за кадр**; всё, что не влезло, списывается. Игра при
перегрузке замедляется — и это правильный выбор: замедление видно и переживаемо,
зависшее окно — нет. `Draw` вызывается ровно один раз за кадр в любом режиме.
`SynchronizeWithVerticalRetrace` остаётся включённым ради картинки, но логика времени
на него не опирается вообще.

Скорости времени — это **частота тиков, а не изменение самой симуляции**: при ×8
оболочка отдаёт 8 тиков за кадр, при ×1/4 — один тик раз в 4 кадра. Симуляция всегда
видит ровно 60 тиков на игровую секунду и о существовании ползунка скорости не знает.
Ступени: пауза, шаг на тик вперёд/назад, ×1/8, ×1/4, ×1/2, ×1, ×2, ×4, ×8 (клавиши —
API-8 §8).

### Машина времени (`TimeMachine`, ядро)

`TimeMachine` — единственный тип, которому разрешено владеть одновременно
`VirtualConsole` и логом ввода; всё остальное время они не знают друг о друге.

- `Advance(int ticks)` — прогнать вперёд, дописывая лог.
- `SeekTo(int tick)` — попасть на произвольный тик. Вперёд — досимулировать; **назад —
  ресимуляция от тика 0**: новая консоль, тот же сид и тот же снимок постоянной памяти,
  прогон лога с подавленным `Draw`, и только последний тик рисуется. Снапшотов в v1 нет
  (ADR-006), контрольная точка ровно одна и она в нуле.
- `Rebuild(Cartridge newCart)` — то же самое, но на **новом** коде: это и есть
  «продолжение» (см. ниже).
- Прогресс — колбэк `Action<int,int>?`, вызываемый не чаще раза в N тиков: в цикле
  ресимуляции аллокаций быть не должно, а вызов делегата на каждый из 108 000 тиков —
  это уже не про аллокации, а про то, что прогресс-бар начинает стоить дороже работы.

### Режим «продолжение» (главная фича вехи M2)

При перекомпиляции картриджа консоль **не** возвращается на старт. Создаётся чистая
консоль на новом коде, и `TimeMachine.Rebuild` прогоняет по ней записанный лог ввода
до текущего тика. Состояние не переносится и переноситься не может — оно
пересчитывается. Совместный эффект ADR-006 и ADR-007: поправил цвет змейки — змейка
той же длины, в том же месте, с новым цветом.

Что при этом обязано быть предусмотрено, потому что «новый код» — это код, которого
раньше не существовало:

- **Новый код падает во время ресимуляции** (например, автор ввёл поле, которого не
  было на 300-м тике). Откат в режим «перезапуск» с честным сообщением, **с указанием
  тика, на котором случился краш** — это единственная подсказка, по которой автор
  поймёт, что сломалось.
- **Ресимуляция дольше 2 секунд** — оболочка показывает прогресс, а не молча морозит
  окно. Дольше 10 секунд — откат в «перезапуск»: ждать десяток секунд после каждого
  `Ctrl+S` хуже, чем начать заново.

### Стоимость ресимуляции

Стоимость линейна по длине сессии, и контрольная точка ровно одна (тик 0), поэтому
цена перемотки назад растёт вместе с сессией: 30 минут игры — это 108 000 тиков,
которые придётся прогнать заново целиком.

**Замер (приёмка M2, `quarp bench carts/snake`).** Windows 11 x64, .NET SDK
10.0.100-rc.2, сборка Release, `carts/snake`:

| Режим | Тиков/сек | Перемотка 30 минут (108 000 тиков) |
|---|---:|---:|
| ресимуляция, живая игра (`--ticks 60`, змейка ещё жива) | ~11 700 000 | **~9 мс** |
| ресимуляция, смешанная (`--ticks 600 --input <лэп>`) | ~27 200 000 | ~4 мс |
| ресимуляция, экран «game over» (`--ticks 100000`, без ввода) | ~95 000 000 | ~1 мс |
| обычная игра вперёд, `Update` + `Draw` | 106 000 – 509 000 | — |

**Перезамер после M3** (та же машина, `quarp bench carts/snake`, у змейки теперь играет тема):

| Режим | Тиков/сек | Перемотка 30 минут | против M2 |
|---|---:|---:|---:|
| ресимуляция, живая игра (`--ticks 60`) | ~647 000 | **~167 мс** | ×18 медленнее |
| ресимуляция, смешанная (`--ticks 600 --input <лэп>`) | ~341 000 | ~316 мс | ×80 медленнее |
| ресимуляция, экран «game over» (`--ticks 100000`) | ~25 200 000 | ~4 мс | ×4 медленнее |
| обычная игра вперёд, `Update` + `Draw` | 147 000 – 185 000 | — | в той же полосе |

Причина одна и она не баг: **синтез идёт на каждом ресимулированном тике**. Путь синтеза
ровно один — иначе перемотанный звук отличался бы от сыгранного, и PCM в golden-master
потерял бы смысл. Тик со звучащей темой стоит ~1,5 мкс против ~85 нс без звука; тик,
на котором всё молчит, стоит только `Array.Clear` на 800 сэмплов (отсюда последняя строка:
змейка после гибели останавливает музыку).

Вывод не меняется: получасовая перемотка стоит **треть секунды в худшем случае**, то есть
на порядок меньше двухсекундного порога показа прогресса и на полтора порядка меньше
десятисекундного отката в «перезапуск» (см. ниже). Дорогой в перемотке остаётся компиляция
Roslyn'ом, а не ресимуляция.

Читать это надо по первой строке таблицы M3: **перемотка получаса игры стоит порядка
167 мс**, и это верхняя оценка — в неё входит `Boot` (`Init` картриджа) на каждый прогон,
которого при реальной перемотке один, а не один на 60 тиков. Разброс между строками
— не шум измерения, а разная работа картриджа на тик: у змейки на экране «game over»
`Update` почти пуст, а музыка остановлена, поэтому «ленивый» замер льстит на порядок.
Ориентироваться следует на живую игру.

**Перепроверено на приёмке этапа 1 вехи M4** (2026-08-18, та же машина, тот же
`quarp bench carts/snake --ticks 60`): обычная игра вперёд (`Update` + `Draw`)
176 173 тика/с, ресимуляция (`Update`) 644 566 тиков/с, то есть 108 000 тиков —
**167,6 мс**, 18 000 тиков (5 минут) — 27,9 мс, 3 600 тиков (минута) — 5,6 мс.
Таблица M3 подтверждена; цифры воспроизводятся, а не были угаданы один раз.

Прежняя оценка «~11 секунд» стояла здесь на выдуманном `Update` в 0,1 мс. Против замера
M2 она была завышена примерно в тысячу раз, против замера M3 со звуком — примерно в
шестьдесят пять: реальный ресимулированный тик змейки — около полутора микросекунд со
звучащей темой и десятки наносекунд без неё, потому что `Draw` при перемотке не
выполняется вовсе (рисуется только финальный кадр, `SeekDrawTail`), а `Update` без
вывода — это арифметика по целым.

Практический вывод после M3 надо формулировать аккуратнее, чем «упираемся в компиляцию,
а не в ресимуляцию»: со звуком это перестало быть правдой. Компиляция Roslyn'ом стоит
десятки–сотни мс **независимо от длины сессии**, ресимуляция — 167,6 мс за получас и
растёт линейно. То есть на коротких сессиях правит компиляция, а примерно после
четверти часа игры ресимуляция её обгоняет и дальше отрывается: минута игры — 5,6 мс,
пять минут — 27,9 мс, полчаса — 167,6 мс, а час — уже треть секунды только на ресим.

Это и есть настоящий срок годности решения «снапшотов в v1 нет» (ADR-006): оно опирается
не на «ресимуляция бесплатна», а на «сессии короткие». Потолок в 10 секунд (см. выше)
для змейки по-прежнему недостижим — он существует ради картриджей, которые считают
на тик несравнимо больше, и ради очень длинных сессий. Следить надо за первой строкой
таблицы: если она ещё раз просядет на порядок, как это случилось при приходе звука,
порог отката начнёт задевать обычную игру, и снапшоты из «не v1» станут задачей.

Путь к мгновенности (не v1): при компиляции картриджа source-generator создаёт
`Snapshot`/`Restore` для полей наследника `Cartridge` — поверхность типов ограничена
(int/Fix/массивы/List), поэтому задача реальна; это снимет причину, по которой снапшоты
отклонены в ADR-006 (бремя ручной сериализации).

### Тест детерминизма (CI, веха M2)

Один и тот же реплей на windows-x64 и linux-arm64 обязан дать одинаковые хэши
framebuffer'а (а с M3 — и PCM). Это golden-master всего проекта, и живёт он в
`.github/workflows/ci.yml`: матрица `windows-latest` / `ubuntu-24.04-arm` (бесплатные
arm64-раннеры — причина, по которой репозиторий публичный, ADR-015), затем отдельный
джоб, который сверяет хэши **между** архитектурами. Сравниваются три вещи: хэш прямого
прогона, `sha256` самого файла `.qrpr` и хэш кадра при проигрывании x64-записи на arm64.
Подробности — REPLAY-FORMAT §6.

## 5. Оболочки

| Оболочка | Технология | Статус |
|---|---|---|
| Desktop | MonoGame (старт на **DesktopGL**; DesktopVK — спайк в M5, см. риски), один `Texture2D`, `DynamicSoundEffectInstance` | M0 (скелет) → M1 |
| Web | .NET wasmbrowser-шаблон (**без Blazor-фреймворка**) + canvas; честная оценка — 500–1000 строк C#+JS: блит через interop, AudioWorklet с ring-буфером, клавиатура/геймпад, RAF-цикл; почти наверняка нужен WASM AOT | M7 (перф-спайк ядра — в M3) |
| Android | MonoGame Android-таргет + экранные кнопки + share/open файлов; hot reload только в режиме «перезапуск» (Mono не выгружает collectible ALC) | M8 |
| iOS | тот же код + Mono-интерпретатор; отдельное решение, см. DECISIONS | стретч |

Примечания:
- DesktopVK появился только в MonoGame 3.8.5 (июль 2026) как платформа первого выпуска;
  наличие linux-arm64-нативок Vulkan-бэкенда не подтверждено. Для одной текстуры 128×72
  разницы GL/VK нет — стартуем на проверенном DesktopGL, решение пересматриваем спайком
  на реальном uConsole в M5 (Vulkan 1.2/1.3 на CM4 есть — v3dv/Mesa).
- Масштабирование: по умолчанию **целочисленное с полями**; опциональный сглаженный
  нецелый режим — настройка оболочки (например, для 256×144 на 1080p, где точный масштаб
  ×7.5). Единая формулировка для README/спеков — отсюда.
- Экспорт в «самодостаточную HTML-страницу» (M7) будет весить ~10–20 МБ (.NET-wasm-рантайм,
  base64) против ~1–2 МБ у PICO-8 — принимаем как данность v1, оптимизация позже.

Оболочка отвечает за: масштабирование, маппинг ввода, звук (очередь 2–3 аудиоблоков,
замер латентности — критерий готовности M3), меню консоли (пауза, реплеи, скриншоты, GIF),
файловые диалоги. Оболочка **не** знает, что такое спрайт или тайл.

## 6. Модель доверия (v1)

Песочницы для чужого C# в .NET не существует (CAS удалён; AssemblyLoadContext — не граница
безопасности; сводка исследования с источниками — [RESEARCH.md](RESEARCH.md)). Поэтому
честная модель:

- Картридж всегда содержит исходный код; консоль показывает его до запуска.
- Запуск чужого картриджа = запуск чужой программы. Предупреждение при первом запуске
  чужого картриджа — в UI оболочки.
- Проверка метаданных (§3) отсекает *случайные* обращения к ОС и сырой интероп, но не
  защищает от намеренно вредоносного кода — и мы этого не обещаем.
- Будущий вариант честной песочницы — компиляция картриджей в WASM (wasmtime на десктопе,
  WACS на мобильных). Отложено: не раньше, чем появится реальный обмен картриджами.

## 7. Инструменты автора (порядок появления)

1. **Внешние редакторы прежде встроенных**: код — VS Code/Rider; спрайты — Aseprite
   (лист — обычный PNG внутри картриджа); карта — свой мини-редактор в оболочке или импорт
   из Tiled (🔶 решить в M4); звук — свой мини-трекер (M3, данные) + UI позже.
2. CLI покрывает весь цикл без GUI: создать, запустить, собрать, проиграть реплей.
3. Встроенные редакторы (спрайты/карта/звук) — веха M9, **живут в оболочке** (обычный UI
   поверх ядра), а не внутри виртуального экрана — в отличие от PICO-8, которая самохостит
   редакторы на своём экране 128×128. Причина: 72 пикселя высоты для IDE непригодны,
   а хостовый UI бесплатно получает мышь, клавиатуру и буфер обмена.
