# Отладка картриджа

**Статус: черновик вехи M4, этап 1 (ADR-019).** Документ описывает то, что уже собрано
и лежит в репозитории. Всё, что проверено не полностью, помечено прямо в тексте —
в проекте про детерминизм «наверное, работает» стоит дешевле, чем ничего.

Картридж Quarp — это обычная сборка .NET, загруженная в живой процесс. Отсюда следует
вещь, которой у PICO-8 нет и быть не может: **штатный отладчик ставит точки останова
прямо в коде игры**, показывает переменные и шагает по строкам. Плюс к этому у нас есть
то, чего нет и у обычного .NET-проекта: **перемотка времени**, то есть возможность
вернуться к тику перед багом и воспроизвести его сколько угодно раз бит-в-бит.

## 1. Что происходит внутри

Понимать это не обязательно, чтобы нажать F5, но полезно, когда что-то не привязалось.

- **Компиляция в память.** `quarp run` читает `src/**/*.cs`, компилирует их Roslyn'ом
  и получает **массив байт**, а не файл на диске. Оптимизация выключена
  (`OptimizationLevel.Debug`), эмиссия детерминированная — при неизменённом исходнике
  байты сборки одинаковы от прогона к прогону.
- **Символы лежат внутри сборки.** Формат отладочной информации — `Embedded`, то есть
  portable PDB упакован в саму DLL. Отдельного `.pdb` рядом нет и не будет — искать его
  бесполезно. Это же обеспечивает номера строк в стектрейсах падений (критерий вехи M1):
  среда выполнения находит символы в образе сама, без второго файла.
- **Собственный контекст загрузки.** Сборка грузится в `AssemblyLoadContext`
  с `isCollectible: true` — по контексту на сборку. Это цена горячей замены: старый
  контекст можно выгрузить, когда на него никто не ссылается. Для отладчика это значит,
  что модуль появляется в процессе **динамически**, а не при старте.
- **Привязка точки останова держится на двух условиях сразу.** Отладчик берёт из PDB имя
  документа и его контрольную сумму. Точка встанет, только если (1) документ указывает
  на файл, который существует на диске, и (2) контрольная сумма документа совпадает
  с байтами этого файла. Второе условие включено ключом `requireExactSource` — это
  настройка по умолчанию у расширения C#, и в сгенерированном `launch.json` она
  оставлена явно. Выключать её нельзя: тогда точка встанет и на разошедшемся файле,
  просто будет показывать не ту строку и не скажет об этом ни слова.

Из третьего пункта следует граница, записанная здесь честно: **отладка по исходникам
работает для папочного картриджа**. У `.quarp8` файлов на диске нет вообще, значит
первое условие привязки выполнить нечем (см. §5).

## 2. Рецепт: F5

1. **Создайте картридж.** `quarp new mygame` кладёт в папку, кроме `manifest.json`
   и `src/main.cs`, ещё два dev-only каталога:

   | Что | Зачем |
   |---|---|
   | `.quarp/cart.csproj` | подсветка диагностик QRP1001–QRP1004 прямо в редакторе (API-8 §12) |
   | `.vscode/launch.json` | конфигурация запуска: F5 запускает картридж под отладчиком |
   | `.vscode/tasks.json` | задача `quarp-build` — проверка компиляции перед запуском |

   Ни один из них не попадает в `.quarp8`, не входит в лимит кода 64 КБ, не меняет
   идентификатор картриджа и не будит горячую замену. Это не обещание, а свойство
   конструкции: загрузчик берёт только `src/**/*.cs` и поимённо названные ассеты,
   упаковщик пишет только этот же список, наблюдатель за файлами фильтрует по
   белому списку. Пинается тестами `VsCodeFolderIsolationTests`
   и `DevProjectIsolationTests`.

2. **Откройте в VS Code папку картриджа**, а не репозиторий Quarp. `launch.json`
   использует `${workspaceFolder}` как путь к картриджу — если открыть что-то другое,
   запустится что-то другое.

3. **Нужно расширение C#** (`ms-dotnettools.csharp`): отладчик `coreclr` живёт в нём.
   Без него VS Code скажет, что тип конфигурации `coreclr` ему незнаком.

4. **Поставьте точку останова** в `src/main.cs`, например на первой строке `Update`.
   До запуска кружок будет полым — это нормально, модуль ещё не загружен.

5. **F5.** Сначала отработает задача `quarp-build` (компиляция картриджа тем же
   компилятором, каким его собирает `quarp run`; ошибки C# и нарушения QRP попадают
   в панель Problems), потом откроется окно консоли. Когда сборка картриджа окажется
   в процессе, кружок станет **закрашенным красным** — точка привязалась.

6. **Остановка.** Отладчик встаёт на строке в первый же тик, который до неё дошёл.
   В панели Variables разверните `this`: там поля вашего картриджа и свойство `Ticks` —
   номер текущего тика. F10 шагает по строкам, F5 продолжает.

### Что именно написано в `launch.json` и почему

| Ключ | Значение | Зачем |
|---|---|---|
| `program` | абсолютный путь к `quarp.exe` | путь к инструментам не относителен папке картриджа; **после переезда картриджа или обновления Quarp файл надо перегенерировать** — та же оговорка, что у `.quarp/cart.csproj` |
| `args` | `["run", "${workspaceFolder}"]` | запускается именно эта папка |
| `justMyCode` | `false` | картридж — сборка, загруженная из памяти в отдельный контекст: ровно такую вещь отладчик вправе счесть «не моим кодом». Оговорка честная: в описании расширения «My Code» исключает код **оптимизированный или без символов**, а картридж не подходит ни под одно из двух, — то есть это дешёвая страховка, а не доказанная необходимость |
| `requireExactSource` | `true` | сверка контрольной суммы источника с PDB; см. §1 |
| `preLaunchTask` | `quarp-build` | ошибки компиляции видны до запуска. Цена честная: картридж компилируется дважды, здесь и внутри `quarp run`. Если быстрый F5 важнее — удалите эту строку |

## 3. Отладка во времени

Симуляция Quarp детерминирована (SPEC-8 §7): одинаковые входы дают одинаковые тики
навсегда. Поэтому «баг на 1200-м тике» — не то, что надо ловить, а то, к чему можно
**прийти**. Способов два, и они не заменяют друг друга.

### Условная точка останова `Ticks == N`

Самый дешёвый способ, штатная возможность отладчика, ничего писать не нужно.
Правой кнопкой по точке останова → *Edit Breakpoint* → *Expression* → `Ticks == 1200`.
Отладчик остановится ровно один раз, внутри `Update` тика 1200.

Годится, когда: вы уже знаете номер тика (например, из стектрейса падения или из
счётчика, который сами вывели на экран) и хотите посмотреть **внутренности** этого тика — локальные
переменные посреди метода, стек вызовов, значения на середине вычисления.

### Флаг `--break-at N`

```
quarp run mygame --break-at 1200
```

Консоль догоняет указанный тик и встаёт на паузу **перед** `Update` этого тика.
В левом нижнем углу появляется `BREAK @1200`, в терминале — строка с точным описанием
состояния. Дальше работают обычные клавиши управления временем: `.` выполняет один тик,
`,` шагает назад, Space снимает паузу, Backspace перематывает.

Годится, когда: отладчика под рукой нет вообще, или вы хотите **пройти тиками** через
подозрительный участок и смотреть на экран, а не в переменные, или собираетесь
подключиться к процессу отладчиком уже после остановки.

**Где здесь единица, о которой надо знать.** Консоль считает тик до того, как его
выполнить: внутри `Update` тика N свойство `Ticks` уже равно N (API-8 §8). Поэтому
«перед `Update` тика N» — это состояние после N−1 тиков, и счётчик тиков консоли
в момент остановки показывает **N−1**. Сделано так намеренно: это ровно тот же момент,
в котором останавливается условная точка `Ticks == N`, — два способа попасть в одну
секунду обязаны попадать в одну и ту же секунду. Нажатие `.` выполняет тик N.

**N = 0.** Тик 0 — это `Init`, у него нет `Update` вообще (API-8 §2). Поэтому
`--break-at 0` и `--break-at 1` называют один и тот же момент: `Init` отработал,
ни одного `Update` не было, счётчик тиков на нуле. Отрицательные значения CLI отвергает.

**Повторяемость.** Два запуска с одним и тем же `--break-at N` дают одинаковый тик
и одинаковый кадр — это проверяется тестами `BreakAtTickTests`, включая случай, когда
кадр оболочки успевает пробежать больше тиков, чем осталось до остановки.

### Связка, ради которой всё затевалось

```
quarp run mygame --break-at 1180     # встали за 20 тиков до бага
.                                    # тик 1180 — смотрим экран
.                                    # 1181
.                                    # ...
,                                    # передумали, шаг назад
Backspace                            # перемотка назад в реальном времени
Home                                 # к самому началу
```

Каждый прогон этой последовательности даёт бит-в-бит одинаковые кадры: перемотка — это
ресимуляция от нуля по записанному логу ввода, а не снимок состояния (ADR-006, ADR-018).
То есть баг, случившийся один раз, можно смотреть сколько угодно раз.

Полезная мелочь, которая следует из устройства оболочки: **пока отладчик стоит на точке
останова, игра не копит пропущенное время**. Аккумулятор тиков банкует не больше
четверти секунды за кадр, а всё, что не влезло в бюджет кадра, списывается
(`TickAccumulator`). Поэтому после продолжения игра не «догоняет» те десять минут,
которые вы провели в отладчике, — она просто идёт дальше.

**Внимание, конфликт клавиш.** F5 в VS Code — «продолжить», F5 в окне консоли Quarp —
«сохранить реплей» (API-8 §8). Клавиша уходит тому окну, у которого фокус. Если хотите
продолжить выполнение — жмите F5, когда фокус в редакторе, а не в игре.

### Без VS Code вообще: пауза, вкладка кода, продолжение (M9, этап 5, ADR-042)

До этого этапа связка выше требовала стороннего окна: `--break-at` или ручная точка
останова стояли в VS Code или Rider, а правка кода всё равно писалась во внешнем
редакторе — окно Quarp только замечало файл на диске. Это ровно то, что ADR-019
назвал первой задачей M4, доведённое до конца: теперь тот же цикл делается **не
выходя из окна консоли**, встроенным редактором кода.

```
Esc              # игра стоит — поднимается меню паузы поверх кадра
F2               # вкладка CODE того же картриджа; сессия жива и на паузе
...               # правите src/main.cs прямо здесь
Ctrl+S           # диск обновлён — CartWatcher замечает файл сам, как и для VS Code
F1               # вкладка GAME; меню паузы снова над кадром, тик тот же
RESUME           # (Enter/Z на пункте, или Esc) — играете дальше на новом коде
```

Механика — та же, что у горячей замены выше: `Ctrl+S` не вызывает перезагрузку
напрямую, он просто пишет файл, а `CartWatcher` — единственный, кто её запускает
(`ShellModeMachine.PollSessionReload` → `CartSession.PollReload` → `TimeMachine.Rebuild`),
той же дорогой, что и правка из-за пределов окна. Разница с VS Code — только в том,
где лежит текст в момент правки: точки останова, стек вызовов и панель Variables
здесь не появляются, это по-прежнему работа внешнего отладчика (§2). Что здесь есть
и чего нет во внешнем редакторе — **сама пауза не требует стороннего окна**: `Esc`
останавливает симуляцию (`CartSession.PauseForEditing`) без потери сессии, а уход
на любую из пяти вкладок редактора паузу не снимает (выше в этом разделе, «Полезная
мелочь» — то же самое правило про несгоревшее время работает и тут).

Работает и вместе с `--break-at`: консоль встаёт на паузе перед нужным тиком, `Esc`
поднимает то же меню поверх уже стоящего кадра, `F2` открывает код, а после `Ctrl+S`
и возврата на `F1` игра ждёт на том же тике с новым кодом — снимать точку и
перезапускать отладчик, как в шаге 5 чек-листа §6, для этого пути не нужно.

Сквозной прогон этой связки — производственный код, а не спайк: `PauseAndContinueTests`
играет картридж, жмёт `Esc`/`F2`, правит текст через `CodeEditorSession`, сохраняет
`Ctrl+S`, ждёт настоящего `CartWatcher` (150 мс debounce) и настоящей Roslyn-компиляции
и проверяет, что тик после возврата на `F1` — тот же самый, а кадр — кадр **нового**
кода, а не перезапуска с нуля; отдельным сценарием — что отмотка на 60 тиков назад
и обратно даёт один и тот же кадр дважды.

## 4. Горячая замена кода под отладчиком

Отредактировать `src/main.cs` во время отладки можно — оболочка увидит правку,
перекомпилирует картридж и **продолжит с того же тика** на новом коде (ARCHITECTURE §4).
Что при этом происходит с точками останова:

- Старая сборка выгружается вместе со своим контекстом, новая загружается в свой.
  Для отладчика это выгрузка одного модуля и загрузка другого.
- Документ в PDB и его контрольная сумма после перекомпиляции соответствуют **новому**
  тексту файла — то есть по контракту привязки (§1) точка остаётся привязываемой.
- **Проверено на стенде** отдельно: если исходник не менялся, детерминированная эмиссия
  даёт байт-в-байт ту же сборку и **тот же MVID**. Значит сразу после перезагрузки
  в процессе могут ненадолго оказаться два модуля с одинаковой идентичностью —
  выгрузка collectible-контекста ленивая, старый умирает не мгновенно.
  **Оговорка, без которой эту фразу прочитают шире, чем она верна:** совпадение
  держится **на одной машине и для одной папки**. С M4 документ в PDB папочного
  картриджа — абсолютный путь (§5), а путь входит в байты сборки; значит те же
  исходники, лежащие в `C:\games\mygame` и в `D:\tmp\mygame`, дают разные байты и
  разный MVID. Сегодня на этом ничего не построено, и строить не надо: сравнивать
  сборки картриджей между машинами следует по идентификатору картриджа (он считается
  по содержимому `src/**/*.cs` и ассетов, а не по путям), а MVID здесь — деталь
  реализации одного процесса.
- **Не проверено:** как настоящий отладчик реагирует на эту пару модулей и
  перепривязывает ли он точку останова фактически. Сквозной прогон под `vsdbg`
  выполнить не удалось (см. §6), поэтому здесь честнее сказать «не знаем», чем
  обещать. Если после горячей замены точка выглядит непривязанной — снимите её
  и поставьте заново; это дёшево и гарантированно работает.

Правка, которую новый код не может пережить (например, исключение на 150-м тике,
которого раньше не было), откатывает сессию в режим перезапуска — об этом оболочка
пишет в терминал с номером убившего тика.

## 5. Известные ограничения

**Отладка по исходникам — только для папочного картриджа.** У `.quarp8` исходников на
диске нет, привязать точку не к чему. Распаковывать пакет во временную папку ради
отладки в M4 не стали: это выглядит как решение, а на деле раскладывает по диску вторую
копию исходников, которая рано или поздно разойдётся с первой. Отлаживайте папку,
пакуйте только готовое.

**Rider не читает `launch.json`.** Своего файла запуска мы для него не генерируем —
это осознанная граница M4. Ручной рецепт: запустить `quarp run mygame` из терминала,
затем *Run → Attach to Process*, найти процесс `quarp` (он же `quarp.exe`), выбрать
отладчик .NET Core, открыть `src/main.cs` и поставить точку. Привязка держится на том же
контракте, что и в VS Code — путь документа плюс контрольная сумма, — так что работать
это обязано одинаково. **Сквозным прогоном не проверено**: Rider на стенде не
запускался.

**Пути в сгенерированных файлах абсолютные.** `launch.json`, `tasks.json`
и `.quarp/cart.csproj` содержат путь к папке с инструментами Quarp. Скопировали картридж
на другую машину или обновили Quarp — перегенерируйте их (`quarp new` в пустую папку,
затем перенести `.vscode` и `.quarp`) или поправьте путь руками. Относительный путь
здесь был бы хуже: он ломается при первом же переносе картриджа, и ломается молча.

**Путь в стектрейсе у папочного картриджа — абсолютный.** Чтобы отладчик мог найти файл,
документ в PDB указывает на файл на диске; тот же путь печатается и в стектрейсе падения:
`at MyCart.Update() in C:\games\mygame\src\main.cs:line 21`. У картриджа, собранного из
источников в памяти (пакет, тесты), путь остаётся коротким: `in src/main.cs:line 21`.
Номера строк — критерий вехи M1 — есть в обоих случаях; меняется только текст пути.

**Тексты диагностик компилятора это не затрагивает.** Пути в ошибках как были
относительными, так и остались — например, на картридже со случайной опечаткой в `Update`:

```
src/main.cs(7,17): error CS1525: Invalid expression term ';'
```

Пример иллюстративный: строка и колонка приходят из Roslyn и зависят от вашего текста,
обещанием конкретных чисел эта запись не является. Постоянна здесь ровно одна вещь —
**путь остаётся относительным** (`src/main.cs`, а не `C:\games\mygame\src\main.cs`),
и так задумано: по этим же относительным путям считается лимит кода и по ним же панель
Problems находит файл в открытой папке картриджа.

## 6. Ручной чек-лист: шесть шагов, минута

Автоматического сквозного прогона под настоящим отладчиком в проекте нет, и это не
лень. `vsdbg` из расширения C# — консольная программа, но она требует криптографического
рукопожатия с клиентом и отказывается начинать отладку словами «.NET Debugging is
supported only in Microsoft versions of VS Code». Отвечать на это рукопожатие — значит
обходить техническое средство защиты лицензии; мы этого не делаем. Поэтому
последний уровень доказательства — руки владельца.

Каждый шаг с ожидаемым результатом. Если результат другой — смотрите таблицу после списка.

1. **`quarp new C:\tmp\dbgtest`**
   → В папке есть `manifest.json`, `src/main.cs`, `.quarp/cart.csproj`,
   `.vscode/launch.json`, `.vscode/tasks.json`. В выводе команды — строка про `.vscode`.

2. **Открыть в VS Code именно `C:\tmp\dbgtest`, нажать F5.**
   → Задача `quarp-build` проходит молча (терминал не открывается), затем появляется
   окно консоли 1280×720 с надписью `HELLO QUARP-8` и белым квадратом (стрелки его двигают).

3. **Поставить точку останова на строке `if (Btn(Button.Left))` в `Update`.**
   → Кружок закрашенный красный. Полый серый кружок означает, что точка не привязалась —
   это отрицательный результат, и его надо доложить, а не обойти.

4. **Дождаться остановки (наступает в тот же тик).**
   → Жёлтая стрелка на этой строке; в панели Variables под `this` видны `_x = 60`,
   `_y = 40` и `Ticks` с текущим номером тика. F10 шагает по строкам `Update`.

5. **Снять точку, поставить условную: правой кнопкой → *Edit Breakpoint* → *Expression*
   → `Ticks == 300`. Перезапустить отладку (Ctrl+Shift+F5), иначе тик 300 уже позади.**
   → Остановка происходит **ровно один раз**, и в Variables `Ticks` равен `300`.
   Это же проверяет, что символы и переменные живут после нескольких сотен тиков,
   а не только на первом.

6. **Остановить отладку. В терминале: `quarp run C:\tmp\dbgtest --break-at 300`.**
   → Окно открывается и сразу стоит на паузе. В левом нижнем углу — `BREAK @300`.
   В терминале — строка `[quarp] --break-at 300: paused before Update of tick 300 —
   the console stands at tick 299...`. Нажатие `.` выполняет тик 300, индикатор
   становится `PAUSE 300`.

### Если не сработало

| Симптом | Скорее всего |
|---|---|
| Полый серый кружок, подсказка «источник отличается от собранного» | контрольная сумма документа в PDB не сходится с файлом на диске (§1). Файл правили после запуска? Перезапустите. Не помогло — это дефект, докладывайте |
| Полый кружок без подсказки, модуль не загружен | картридж не дошёл до загрузки: смотрите Debug Console, там ошибки компиляции |
| VS Code не знает тип `coreclr` | не установлено расширение C# (`ms-dotnettools.csharp`) |
| F5 запускает не тот картридж | открыта не папка картриджа; `${workspaceFolder}` указывает на то, что открыто |
| F5 «сохранил реплей» вместо «продолжить» | фокус был в окне игры, а не в редакторе (§3) |
| Задача `quarp-build` не находит команду | картридж переехал или Quarp обновился — перегенерируйте `.vscode` (§5) |
