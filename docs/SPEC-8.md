# Спецификация: Профиль 8

**Статус: РАТИФИЦИРОВАНА (2026-08-19, решение владельца по протоколу гриля — ADR-024;
вместе с `API-8.md`).** Документ перманентен: существующие правила, размеры и вызовы
не меняются и не удаляются; добавления возможны только через ADR. Жизненный цикл
(ADR-012) пройден полностью: заморозка в M0 → шесть сыгранных прототипов и замеры
вехи M4 → финальная ратификация.

Философия профиля: «самая маленькая игра, которую не стыдно закончить».
Ориентир по духу — PICO-8, но с широким экраном и C#.

## 1. Экран

| Параметр | Значение |
|---|---|
| Разрешение | **160×90**, соотношение 16:9 (ADR-021, окончательно) |
| Сетка тайлов | **20 × 11.25** тайлов по 8×8 — нецелая по вертикали, см. ниже |
| Частота кадров | 60 FPS (привязана к тикам, см. §7) |
| Буфер | индексированный, 1 байт на пиксель: **мастер-индексы 0–31** (§2) |
| Системный шрифт | 4×6 px → **40 колонок × 15 строк** текста (мелкий, `Font.Small`; второй шрифт — API-8 §3, ADR-022) |

Буфер хранит не слот видимой палитры, а **мастер-индекс 0–31** — то, что осталось от
слота после ремапа `Pal`. Рисующие вызовы принимают слот видимой палитры **0–15**
(значение маскируется `& 15`), консоль подставляет мастер-цвет из этого слота и кладёт
в буфер уже его. Ограничение «≤ 16 цветов на кадре» это не нарушает: за кадр
одновременно доступны ровно 16 слотов, но их мастер-индексы — любые из 32.
`Pget` возвращает мастер-индекс (API-8 §3), оболочка переводит его в RGB по таблице §2.

**Разрешение — вердикт владельца по итогам шести прототипов «худших жанров»**
(платформер, вертикальный шмап, диалог, копатель, брейкаут и живая змейка; метрики
объявлены до написания игр и сведены в `M4-MEASUREMENTS.md`; протокол решения —
ADR-021). 160×90 выиграло не геометрией самой по себе, а тем, что это единственное
разрешение своего класса с целым масштабом на всех распространённых дисплеях:

| Дисплей | Масштаб |
|---|---|
| uConsole / 720p | ×8 — пиксель-в-пиксель, окно оболочки по умолчанию |
| 1080p | ×12 |
| 1440p | ×16 |
| 4K | ×24 |

Арифметический паритет с PICO-8 (176×99, +6 %) не целый нигде (1080/99 = 10.9);
192×108 целое, но теряет 720p (6.67) и раздувает площадь на +27 % к PICO-8. Теснота
как характер консоли сохранена: 14 400 пикселей — меньше, чем у PICO-8 (128×128 =
16 384), заметно меньше TIC-80 (240×136).

**Что решил спор со 128×72.** Действие на меньшем экране было честным (платформер
с камерой-с-упреждением брал порог реакции Р7 впритык, запас 0.00 тика; валуны
копателя были видны). Умер текст: окно диалога на 128×72 съедало 43.1 % экрана
против 34.4 % на 160×90, а строчный шрифт 3×5 был на грани различимости — и это
единственное, что владелец почувствовал глазами на плейтесте. Асимметрия рисков
решила в пользу большего экрана: ошибка в сторону 128 после ратификации была бы
перманентной, ошибка в сторону 160 стоила бы неделю работы, которая уже сделана.
Вариант 160×88 («ради целых тайловых рядов») отклонён — не 16:9, не целый масштаб;
вариант 160×96, рассматривавшийся раньше, — тоже (не 16:9, не пиксель-в-пиксель на
720p, ADR-005).

**Постоянный дефект, принятый осознанно.** 90 / 8 = **11.25**: тайловая сетка по
вертикали не целая — 11 полных рядов (88 px) плюс полоска **2 px** под неполный
двенадцатый ряд. Прецедента в нише у этого размена нет — он наш собственный:
TIC-80 выбрал наоборот (240×136 — сетка целая, 30×17 тайлов, зато соотношение
1.76 вместо честных 16:9 и нет целого масштаба на бытовых дисплеях); мы отдали
целую сетку за точный 16:9 и целый масштаб везде.
Игры не имеют права зашивать «12 рядов» константой — правильный рецепт: считать
видимые полные ряды целочисленным делением высоты игрового поля на размер тайла,
`visibleRows = fieldH / TileSize` (рецепт из `carts/digger`, уже живёт в коде демо).
Неполный ряд не участвует в игровой сетке (коллизии, тайловая логика), но остаётся
на экране — использовать его под HUD-подложку или декоративную кайму можно,
обязательного требования прятать его нет.

Прямые порты с PICO-8 (128×128) и TIC-80 (240×136) по-прежнему требуют редизайна
экранов: 20 колонок тайлов у нас против 16/30 у прототипов, и высота считается
делением, а не константой. Хорошо живут: горизонтальные скроллеры и шмапы, раннеры,
гонки, файтинги, змейки, головоломки, топ-даун с «коридорными» комнатами, диалоги
и текстоёмкие сцены — последнее и есть главный выигрыш переезда с 128×72
(`M4-MEASUREMENTS.md`: окно реакции платформера с камерой-с-упреждением получает
запас 3 тика на 160×90 против нуля на 128×72).

## 2. Цвет

Модель зафиксирована (ADR-016, по итогам исследования сообществ — [RESEARCH.md](RESEARCH.md)):

- **16 видимых цветов** — фиксированы навсегда, менять RGB нельзя. Фиксированная палитра —
  визуальная идентичность консоли (сообщество PICO-8 защищает это правило само: «игру
  узнают по цветам, как когда-то игры на C64»).
- **16 «секретных» цветов** (индексы 16–31) — тёмные/светлые двойники видимых,
  спроектированные с ними как **единый мастер-набор из 32**. Использование: затемнения,
  ночные палитры, недостающие оттенки — самая любимая цветовая фича жанра.
- На экране всегда ≤ 16 цветов за кадр (кадру доступны ровно 16 слотов; в буфер пишется
  мастер-индекс слота, см. §1): любой из 16 слотов
  можно перенаправить на двойника документированным вызовом `Pal(slot, color)` —
  API первого класса, а не магический poke (урок PICO-8: фичу любят, к доступу — претензии).
- Прозрачность: цвет 0 по умолчанию прозрачен при отрисовке спрайтов (переопределяется `Palt`).
- Палитра **оригинальная**, не заимствованная: чужая консольная палитра — клеймо клона
  (LIKO-12), путь PICO-8/Pyxel — своя. Требования, зашитые в дизайн (из жалоб сообществ
  на чужие палитры): полноценные синие, коричневый и ≥2 тонов кожи, тёплые И холодные
  тёмные, серая рампа для дизеринга через весь набор 32, яркость без «мрака».
- **Hex-значения — финальные** (решение владельца 2026-08-19, гриль палитры; формально
  ратифицируются вместе со спекой). Видимые 16 — черновик v1 без правок: их валидировали
  шесть демо, галерея чужого профессионального арта и данные спроса ниши (RESEARCH,
  «Лимиты» и палитровая разведка). Парные оттенки — v2: одиннадцать из шестнадцати
  получили ремесленный сдвиг тона при сохранённой светлоте — тени холодной семьи уходят
  в сине-фиолетовое, тени тёплой идут по кругу к ржаво-винному, как в рисованном вручную
  пиксель-арте; контраст затемнения не изменился ни на волос.

| # | Видимые 0–15 | # | Парные оттенки 16–31 |
|---|---|---|---|
| 0 | `#1d1626` чернильный | 16 | `#383052` сумеречный |
| 1 | `#6e7b8f` серый | 17 | `#424b70` ночная сталь |
| 2 | `#b9c2cf` светло-серый | 18 | `#8591ab` пепельный |
| 3 | `#f7f3e8` белый | 19 | `#ddd4c2` пергамент |
| 4 | `#2c3e8c` синий | 20 | `#191b55` ночной |
| 5 | `#46a1e0` небесный | 21 | `#3262a0` стальной |
| 6 | `#2f9e8f` бирюзовый | 22 | `#1d5e62` морской |
| 7 | `#55c04b` зелёный | 23 | `#2d753c` лесной |
| 8 | `#f7d94c` жёлтый | 24 | `#cb952a` янтарный |
| 9 | `#ef9433` оранжевый | 25 | `#b4561f` ржавый |
| 10 | `#d8434e` красный | 26 | `#7f2842` винный |
| 11 | `#ea6bb0` розовый | 27 | `#a6478e` сливовый |
| 12 | `#8348a8` фиолетовый | 28 | `#4d2c76` тёмно-лиловый |
| 13 | `#8a5535` коричневый | 29 | `#55301d` умбра |
| 14 | `#cf9367` загар | 30 | `#a5714a` глина |
| 15 | `#f3cfa7` кожа светлая | 31 | `#ffe9d1` персиковый |

**Правило пар и два именованных исключения.** Каждый парный оттенок темнее своего
видимого — кроме пары **0→16** (темнее почти-чёрного не бывает; 16 — подсветка тьмы,
тот же приём у PICO-8) и пары **15→31** (персиковый — тёплый хайлайт светлой кожи
и четвёртый телесный тон, не тень). Слово «тёмный двойник» из ранних черновиков
уходит: 16–31 — **парные оттенки**, их роль шире затемнения.

**Три рецепта практики** (каждый куплен настоящим багом или находкой M4):
1. **Тёмная кожа — это загар 14 (тень — умбра 29/глина 30), а не 31**: персиковый
   светлее кожи, «затемнение» им осветляет (ловушка, найденная бригадой диалога).
2. **Один слот — один объект сцены**: слот, который красит и персонажа, и фон,
   заставит их сливаться при любом `Pal`-своп (мигающий моряк плейтеста M4).
3. **Ночная сцена — `Pal(i, i+16)` для всех шестнадцати**: парный набор спроектирован
   так, чтобы включённый целиком он читался единой ночью, а не потемневшим днём.

**Принятый компромисс, записанный осознанно:** второго зелёного (лайма) в видимых
шестнадцати нет — он есть в большинстве топ-палитр ниши, и галерейный перенос чужого
арта показал цену (листва делит один зелёный с бирюзой). Жертвовать оказалось некем:
каждый слот-кандидат на замену доказал свою нужность демо или галереей. Лайм — цена
шестнадцати слотов, как и у самой PICO-8.

**Дополнение к §2 (ADR-034, 2026-08-25): у палитры две стадии, а не одна.**
Ратифицированный текст выше не меняется ни словом: 16 видимых, 16 парных, 32 мастера,
hex финальные, `Pal(slot, color)` работает ровно как описано. Дополняется то, о чём
§2 не говорил вообще, — **сколько в консоли ремапов и на каком этапе они применяются**.
Стадий две:

| Стадия | Когда применяется | Что задаёт | Чем видна |
|---|---|---|---|
| 1. Рисующая — `Pal` | в момент записи пикселя | какой мастер-цвет ляжет в буфер за слот 0–15 | буфером: `Pget`, `FrameHash` |
| 2. Выводящая — `Pald`/`Palr` | при выводе кадра на экран | как показывается то, что уже в буфере | вторым хэшем; буфер не меняется |

Вторая стадия — это **четыре набора** по 32 байта (`набор[k][мастер] → мастер`,
по умолчанию все четыре тождественны) плюс **селектор по строкам**: по одному номеру
набора на строку экрана, по умолчанию нули. Правило вывода целиком:
`цвет = МАСТЕР[ набор[ селектор[y] ][ пиксель[x, y] ] ]`. Вызовы, маскирование
аргументов и краевые случаи — API-8 §3 (`Pald`, `Palr`).

Что это НЕ меняет:

- **Буфер прежний** — 1 байт на пиксель, мастер-индексы 0–31 (§1). Вторая стадия
  в него не пишет ничего и не читается из него ничем.
- **«≤ 16 цветов за кадр» держится ровно как держалось**: рисующие вызовы по-прежнему
  берут слот 0–15, кадру доступны те же 16 слотов. Вторая стадия не добавляет кадру
  ни одного нового цвета — она перекрашивает уже присутствующие; больше 16 разных
  мастер-цветов в кадре может появиться только построчно, потому что разные строки
  вправе показываться через разные наборы.
- **Хэш кадра прежний.** `FrameHash` считается по индексному буферу и отвечает на
  вопрос «что нарисовал картридж»; состояние вывода в него не входит и войти не может.
  Состояние вывода — 218 байт (4 × 32 + 90) — измеряется **вторым** хэшем тем же
  FNV-1a и в том же текстовом виде (16 строчных hex-цифр), отвечающим на вопрос
  «как это раскрашено». Кадр описывается парой этих величин; ни одна из них по
  отдельности кадр не описывает.
- **Состояние вывода — состояние рисования, а не симуляции** (§7): оно живёт до явной
  смены, сбрасывается вместе с камерой, клипом и палитрами при подключении картриджа,
  и ресимуляции воспроизводить его не нужно.

## 3. Графические данные

| Ресурс | Лимит | Память |
|---|---|---|
| Лист спрайтов | 128×128 px = **256 спрайтов 8×8** | 8 КБ (4 бита/пиксель) |
| Карта (map) | **256×72 тайлов** (~12.8 × 6.4 экрана 20×11.25; со старой сеткой 128×72 это было ровно 16×8 экранов — размер карты переезд не менял, ровное деление ушло вместе с целой сеткой) | 18 КБ (1 байт/тайл) |
| Флаги спрайтов | 8 флагов на спрайт | 256 байт |

- Спрайт рисуется командой `Spr` с зеркалированием по X/Y; «большие» объекты собираются
  из соседних клеток листа (`Spr(n, x, y, w, h)`).
- Вращения и растяжения спрайтов (`Sspr`) в профиле 8 **нет** — осознанно: целостность
  пиксельной сетки; и то и другое есть в профиле 16. Решение записано, чтобы после
  ратификации на «а добавьте sspr как в PICO-8» был готовый ответ.
- Слоёв карты один; параллакс и «второй слой» достигаются повторными вызовами `Map`
  с разными регионами и смещениями.

## 4. Звук

| Параметр | Значение |
|---|---|
| Выход | **моно** (решено, ADR-013; NES тоже был моно — стерео это профиль 16) |
| Каналы | **4** |
| Волны | pulse 12.5% / 25% / 50%, triangle, saw, noise |
| SFX | 64 слота × 32 шага (нота, волна, громкость, эффект) |
| Эффекты ноты | slide, vibrato, drop, fade in/out, arpeggio |
| Музыка | 64 паттерна × 4 канала, зацикливание, флаги секций |

Звук синтезируется ядром в **целочисленной арифметике** — PCM бит-идентичен на всех
платформах и входит в golden-master-тесты (ARCHITECTURE §2).

Обе таблицы — 64 слота и 64 паттерна — картридж может **заменить целиком** из банка данных:
`DataToSfx`, `DataToMusic` (§6, ADR-036, API-8). Это предел, а не окно: одновременно звучащих
слотов по-прежнему 64, просто игра крупнее одного набора банков возит остальные эпизоды рядом
и переключает их на границе уровня. Писать таблицу по одному слоту или по одному шагу нечем —
`Sfxset` в профиле 8 нет.

## 5. Ввод

- До **2 игроков**.
- На игрока: D-pad (4), кнопки **O** и **X**, **Start** (пауза/меню).
- Источники: клавиатура, геймпад, на Android — экранные кнопки. Маппинг — забота оболочки,
  картридж видит только логические кнопки.
- Мыши и текстовой клавиатуры в API профиля 8 **нет** (осознанно: игры должны быть играбельны
  на устройстве с геймпадом).

## 6. Картридж

У картриджа **две физические формы, и это один и тот же картридж**: рабочая папка автора
и файл `*.quarp8` — та же раскладка, упакованная zip'ом без обёрточной папки. Обе формы
грузятся одним загрузчиком, дают одинаковые данные консоли и одинаковую идентичность
(REPLAY-FORMAT §5). Разница ровно одна: у папки исходники лежат на диске, поэтому
отладка по исходникам работает только с ней (DEBUGGING.md).

**Состав пакета.** Записи перечислены в том порядке, в каком их пишет упаковщик;
`src/**` — по возрастанию пути, ординальным сравнением.

| Запись | Обязательна | Размер / формат | Что проверяется при загрузке |
|---|---|---|---|
| `manifest.json` | да | JSON-объект | `name` — непустая строка; `profile` — целое, ровно `8`; `author` — строка, по умолчанию пустая; неизвестные свойства игнорируются |
| `src/**/*.cs` | да, хотя бы один файл | UTF-8, BOM снимается | наличие хотя бы одного; лимит кода |
| `gfx.png` | нет | ровно 128×128 | PNG: типы цвета 3/2/6, глубина 8, без интерлейса; палитра (ниже) |
| `map.bin` | нет | ровно **18 432** байта (256×72, §3) | длина |
| `flags.bin` | нет | ровно **256** байт (§3) | длина |
| `sfx.bin` | нет | ровно **4360** байт | магия `QSFX`, версия, геометрия, каноничность шагов (AUDIO-FORMAT §2, §7) |
| `music.bin` | нет | ровно **328** байт | магия `QMUS`, версия, геометрия, каноничность (AUDIO-FORMAT §4) |
| `cover.png` | нет | ровно 160×90 (ADR-021) | **ничего** — см. «Известные дыры v1» |
| `data/NN.bin` | нет | `NN` — две цифры `00`..`63`; ≤ 1 МиБ на банк, ≤ 4 МиБ на все вместе (ADR-035) | номер и обе длины |

- **Банки данных (ADR-035)** — произвольные байты, которые игра читает по ходу
  (`DataGet`, `DataToGfx`, `DataToMap`, а с ADR-036 ещё `DataToSfx` и `DataToMusic`, API-8).
  Они и есть ответ консоли на игру крупнее одного набора банков; найден вопрос на порте POOM,
  где одна игра просит 88 КБ данных против 26 КБ банков профиля 8, а её звук — около 100
  слотов SFX и 71 паттерн против 64 и 64 (§4). Банк, из которого подкачивается звук, несёт
  ровно те же payload'ы, что `sfx.bin` и `music.bin`, без их 8-байтовых заголовков
  (AUDIO-FORMAT §2, §4): отдельной записи в пакете для этого не заводится. Банки участвуют в идентичности картриджа
  (REPLAY-FORMAT §5) — **но только когда хоть один из них непустой**: картридж без банков
  означает ровно то же, что означал до их появления, и его идентичность не сдвигается,
  иначе от него отвязался бы каждый уже записанный реплей.
- **Отсутствующий необязательный ассет = нули.** Пустая карта, пустые флаги, чистый лист
  спрайтов, 64 пустых слота SFX и 64 пустых паттерна. Картридж без звука — молчащий,
  а не сломанный, и грузится он как картридж с пустым банком, байт в байт.
- **Исходный код в картридже присутствует всегда** — открытость вместо песочницы. Пакет
  без единого `src/**/*.cs` — ошибка загрузки.
- **Имена — строчными, ровно как написано.** В пакете они сравниваются побайтово; полагаться
  на то, что файловая система папки нечувствительна к регистру, нельзя: `GFX.PNG` откроется
  на Windows и не откроется на Linux и никогда — из пакета.
- **Записи, которых нет в таблице, игнорируются**, как и записи-каталоги. Упаковщик их
  не создаёт; правило нужно для пакетов, собранных чем-то ещё.
- **Одна распакованная запись ≤ 4 МиБ** — предел против zip-бомбы, не выразительное средство.
- **Упаковка детерминирована**: у всех записей фиксированное время (2000-01-01T00:00:00Z),
  порядок задан выше, поэтому две упаковки неизменившейся папки дают побайтово равные файлы.

**Что в пакет не попадает.** Пакет — это собранная игра, а не рабочая папка. Из папки
не едет ничего, кроме перечисленного выше, и в частности:

| Не едет | Почему |
|---|---|
| `map.csv` | исходник карты; консоль играет `map.bin` (MAP-FORMAT.md) |
| `sfx.txt`, `music.txt` | исходники банков; консоль играет `sfx.bin` / `music.bin` (AUDIO-FORMAT §6) |
| `.vscode/**` | конфигурация отладчика с абсолютными путями машины автора (DEBUGGING.md) |
| `.quarp/**` | dev-проект для IDE и его `obj/` |
| `replays/**` | записи сессий; к игре они не относятся |
| `save.dat` | прогресс игрока, а не игра |
| всё остальное | `gfx.aseprite`, `README.md`, заметки — по тому же правилу |

Для каждого dev-only файла утверждений четыре, и ломаются они независимо, поэтому
проверяются по отдельности: **не попал в пакет; не вошёл в лимит кода; не изменил
идентичность картриджа; не разбудил горячую замену.** Горячая замена реагирует на
`manifest.json`, `src/**/*.cs` и пять собранных ассетов — на результат сборки, не на её
исходник: иначе перезагрузка случалась бы на каждое нажатие клавиши в текстовом редакторе
и не меняла бы ничего из того, что видно и слышно.

Папочная форма — единственная, где исходники ассетов вообще могут лежать рядом, поэтому
она же единственная, где ловится самая неприятная ошибка автора: **`sfx.txt` есть,
`sfx.bin` нет — отказ загрузки с именем команды, которая это чинит** (то же для `music.txt`).

**Лимиты.**

- **Размер: файл `.quarp8` (сжатый) ≤ 320 КБ** (327 680 байт) **без учёта `data/`**.
  Проверяется дважды — при упаковке (переросший файл не создаётся) и при загрузке. Число
  выбрано арифметикой, а не надеждой на сжатие: 256 КБ кода сырыми + ~31 КБ ассетов сырыми
  (их размеры зашиты форматами) + запас на манифест и обложку — картридж влезает даже при
  нулевом сжатии, поэтому предсказуемый лимит кода всегда бьёт первым (урок «сжатого метра»
  PICO-8, который наказывал авторов с непредсказуемой стороны, — ADR-024).

  *Поправка, ADR-036.* Изначально здесь стояло «≤ 320 КБ» на весь файл, и это противоречило
  ADR-035: банки данных ратифицированы отдельно, до 1 МиБ на банк и 4 МиБ суммарно, то есть
  разрешённый картридж заведомо не влезал в собственный лимит пакета. Нашёл противоречие
  порт POOM — 514 КБ банков на шесть уровней, — и нашёл только потому, что до `quarp pack`
  никто с таким картриджем не доходил. Арифметика выше про код и ассеты и всегда была про
  них; банки считаются по своим лимитам (§6, `data/NN.bin`), и оба предела остаются
  предсказуемыми по отдельности.
- **Код: ≤ 256 КБ** (262 144 байта) — байты UTF-8 всех `src/**/*.cs` **после удаления
  комментариев** (comment trivia через Roslyn SyntaxTree) и нормализации переводов строк
  в `\n`. Комментарии бесплатны — намеренно: исходники картриджей читают люди, и лимит
  не должен наказывать за читаемость. Считается по обеим формам одинаково. Величина
  выбрана на грилле ратификации по замерам (ADR-024): Rogue 1980 — 281 КБ нашей метрикой,
  Pixel Dungeon — 1220 КБ чистой игровой логики; 256 КБ вмещают Rogue-глубину, написанную
  под платформу, а игры класса Pixel Dungeon — территория профиля 16.
- **Ровно один наследник `Cartridge`** на весь картридж: ноль — ошибка, два и более —
  ошибка с именами найденных типов; конструктор обязан быть публичным и без параметров.
  Это тоже лимит формата, а не деталь API: сюда за полным списком отсылает API-8 §12.
- **Сохранения вне лимита картриджа**: 64 ячейки постоянной памяти (`Dget`/`Dset`) по
  4 байта. Живут рядом с картриджем в `save.dat`, в пакет не входят.

**Палитра `gfx.png`.** Каждый непрозрачный пиксель обязан **точно** совпадать с одним
из 16 видимых цветов палитры (§2), иначе — **ошибка сборки с координатами пикселя**.
Полностью прозрачный пиксель — индекс 0; частичная прозрачность — ошибка. Никакого
«ближайшего цвета»: это маскировка ошибок, а картридж с тихо перекрашенным артом
выглядит не так, как его нарисовали, и автору об этом никто не скажет.

**Версия формата.** Собственного номера версии у контейнера `.quarp8` нет: селектор
раскладки — `profile` в манифесте (`8` — этот документ, `16` — SPEC-16). Свои версии
в заголовках несут только звуковые банки (AUDIO-FORMAT §1). Правило обращения с номером
версии — общее для всех форматов проекта и выведено в **AUDIO-FORMAT §7**:

> **номер версии описывает раскладку байтов, а не строгость валидатора.**

Меняется раскладка или смысл поля — новая версия и явная конвертация. Загрузчик начинает
ловить то, что спецификация запрещала и раньше, — это исправленный загрузчик, а не новый
формат: файл, который под правило не подходил, был вне спецификации и в старой версии,
и поднятием номера он не спасается.

**Что с момента ратификации меняется только через ADR:**

- состав пакета — любая новая запись, удаление существующей, перевод dev-only файла
  в состав пакета или обратно;
- обязательность любой записи;
- любой из фиксированных размеров: 128×128, 18 432, 256, 4360, 328, 160×90;
- лимиты 320 КБ (пакет) и 256 КБ (код) **и способ их подсчёта**;
- правило палитры `gfx.png`;
- набор того, что входит в идентичность картриджа (это вдобавок обесценивает все
  записанные реплеи — REPLAY-FORMAT §5).

Ужесточение проверки до того, что спецификация и так требовала, ADR не требует — это
прямое следствие правила версии выше.

**Известные дыры v1** (записаны честно, потому что после ратификации умалчивание дороже):

1. **`cover.png` не проверяется ничем.** Требование «ровно 160×90» (ADR-021) — требование к автору;
   v1 кладёт файл в пакет как есть и не читает его ни при упаковке, ни при загрузке.
   Закрытие этой дыры — исправленный загрузчик, а не новая версия формата.
2. **Сборка не умеет сказать «этот картридж собран более новым Quarp»**: неизвестные
   свойства манифеста игнорируются, а номера версии у контейнера нет. Дыра того же рода,
   что отсутствие версии ядра в реплее (REPLAY-FORMAT §7).

## 7. Модель времени и детерминизм

Ключевое требование проекта. Правила:

1. **Фиксированный тик: 60 тиков/сек.** `Update()` вызывается ровно 60 раз на игровую
   секунду, независимо от FPS и железа. `Init()` — «тик 0», часть детерминированной
   симуляции.
2. **`Draw()` не меняет состояние.** Всё состояние игры меняется только в `Init`/`Update`.
   (Соблюдение — конвенция + анализатор; технически не запрещено.)
3. **float и double запрещены во всём коде картриджа — включая `Draw`.** Только `int` и
   **`Fix`** (fixed-point Q16.16, диапазон **[−32768; +32768)** с шагом 1/65536) — как на
   настоящем ретро-железе, где FPU не было. Почему целиком, а не только в `Update`:
   (а) это делает *кадр*, а не только логику, бит-в-бит одинаковым на x64/ARM64 — хэш
   framebuffer'а становится честным кросс-платформенным golden-master-критерием;
   (б) анализатор превращается из межпроцедурного анализа в тривиальный бан типов.
   Поведение `Fix` при переполнении и делении на ноль фиксируется в `API-8.md`
   (любой вариант, но детерминированный и записанный).
4. **Математика и случайность — только консольные.** `SMath.Sin/Cos/Sqrt/Atan2` (на `Fix`,
   табличные — 1024 узла на четверть с лерпом, бит-в-бит одинаковые везде; измеренная
   точность синуса 2.2e-5). **Углы — в оборотах**: 1.0 = полный круг, 0.25 = четверть,
   как в PICO-8 (ADR-014). RNG — xoshiro128\*\*, состояние — часть симуляции;
   пользовательский сид разворачивается через splitmix64 (нулевое состояние невозможно).
5. **Запрещено в коде картриджа** (ловит анализатор): `System.Random`, `DateTime`, `Guid`,
   `Environment`, `Task`/`Thread`/`async`/`await`, культуро-зависимые `ToString`/`Parse`,
   явный `object.GetHashCode`.
6. **Порядок обхода коллекций.** `Dictionary`/`HashSet` нельзя итерировать в симуляции:
   .NET рандомизирует хэши строк на каждый запуск процесса, порядок обхода различается
   между машинами — реплей разойдётся именно между устройствами, в самый неудобный момент.
   Обходить только массивы, `List`, либо отсортированные ключи. Анализатор предупреждает
   о `foreach` по словарю/сету. Оболочка дополнительно выставляет инвариантную культуру
   процесса.
7. **Входы симуляции: кнопки + снимок постоянной памяти.** Реплей = версия картриджа +
   сид + снимок `Dget`-памяти на момент записи (256 байт) + лог ввода по тикам.
   При проигрывании реплея `Dset` пишет в копию, не в реальные сохранения игрока.
   (Постоянная память — второй внешний вход; без её снимка реплей не воспроизводим.)

Отсюда бесплатно: перемотка вперёд (симуляция без отрисовки), назад (ресимуляция от
контрольной точки), замедление, реплеи, одинаковость на любом железе. Стоимость ресимуляции
линейна по длине сессии — честные цифры и план снапшотов: ARCHITECTURE §4.

Бюджет производительности (ориентир, не жёсткий лимит): `Update` ≤ 2 мс на Raspberry Pi CM4.
Жёсткого счётчика «виртуальных циклов CPU» в v1 нет — честно признаём, что детерминирован
*результат* симуляции, а не её *стоимость*.

## 8. API картриджа (эскиз поверхности)

Картридж — класс, унаследованный от `Cartridge`. Ратифицируемая («железная») поверхность —
это `IConsoleApi`, его protected-зеркала на `Cartridge`, свойство `Cartridge.Q` и типы
`Fix`/`SMath`/`Button`/`Font`; она сознательно крошечная (~35 вызовов) и после ратификации
перманентна. **Библиотека `Quarp.Api.Std` в железо НЕ входит**: это обычный C#-код
в той же сборке (готовые помощники, вырезанные из повторов демо — ADR-019), он растёт
и правится после релиза без ADR, не съедает лимит кода картриджа и не участвует
в перманентности. Граница проста: железо — то, что умеет консоль; Std — то, что удобно
автору (ADR-024, Р31).

```csharp
public class MyGame : Cartridge
{
    Fix x;

    public override void Init()            // «тик 0», часть симуляции
    {
        x = 60;
    }

    public override void Update()          // 60 раз в секунду, вся логика тут
    {
        if (Btn(Button.Right)) x += Fix.Ratio(1, 2);   // 0.5
    }

    public override void Draw()            // только рисование, состояние не менять
    {
        Cls(1);
        Map(0, 0, 0, 0, 20, 12);   // 12-й ряд тайлов срезается клипом: 90/8 = 11.25 (§1)
        Spr(1, (int)x, 40);
        Print("HELLO", 4, 4, 7);
    }
}
```

Группы API: `Init/Update/Draw` ·
`Cls/Pset/Pget/Line/Rect/RectFill/Circ/CircFill/Spr/Map/Mget/Mset/Fget/Fset/Print/Camera/Clip/Pal/Palt`
(плюс `Pald/Palr` — вторая стадия палитры, дополнение §2, ADR-034) ·
`Btn/Btnp` · `Sfx/Music` · `Fix/SMath/Rnd/Srand` · `Dget/Dset` · `Ticks` (счётчик тиков).

Точная сигнатура каждого вызова фиксируется в M1 отдельным документом `API-8.md`,
ратифицируется вместе со спецификацией (конец M4). В `API-8.md` обязателен раздел
«рассмотрено и решено» с письменным «да/нет и почему» по предсказуемым запросам
сообщества: fill-паттерны (`fillp`), `Oval`, `Sget`/`Sset` (пиксели листа спрайтов),
`Print` с возвратом ширины текста, `Sspr` (решение уже записано в §3: нет в профиле 8),
а также способ записи дробных констант `Fix` (`Fix.Ratio`, готовые константы,
поведение при непредставимых значениях). Уже решено и записано в ADR-014: углы в оборотах,
устройство и точность `SMath.Sin/Cos`, отказ от SoftFloat как типа симуляции.
