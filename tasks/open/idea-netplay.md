# Простые сетевые игры — предложение владельца и почти готовый фундамент

Идея владельца (2026-08-18): дать авторам возможность делать простые, НО сетевые
игры — «возможно неосуществимо, но записать стоит: мощный способ выделиться».
Ниша подтверждает: ни PICO-8, ни TIC-80, ни LIKO-12 встроенного нетплея не имеют —
только костыли сообщества.

**Архитектурный факт, который делает идею осуществимее, чем кажется: самое
трудное в нетплее у нас уже построено.** Классический lockstep/rollback-неткод
(файтинги, RTS, GGPO) требует ровно трёх вещей:
1. детерминированная симуляция, бит-в-бит одинаковая на разных машинах —
   у нас ЭТО ДОКАЗЫВАЕТСЯ кросс-арх CI на каждом коммите (M2);
2. быстрая ресимуляция для отката — есть, ~647 тыс. тиков/с (M3);
3. пересылать только ввод — вся наша модель времени и так «лог ввода + тик»
   (реплеи, машина времени M2).
Плюс: API уже мультиплеерный (`Btn(button, player)`), и картриджу для нетплея
НЕ НУЖНО НИ ОДНОГО нового вызова — оболочка подаёт ввод удалённого игрока в тот
же поток тиков; игра даже не знает, что она сетевая. Ратифицируемый API-8 этим
не задевается вовсе. Десинк-детект бесплатный: наши покадровые хэши и есть
контрольные точки для сверки.

**Честные трудности (почему XL и почему после M7):** транспорт и NAT (UDP/relay;
в вебе — WebRTC DataChannel), матчмейкинг/лобби, стратегия задержки
(delay-based для простых игр дешевле rollback), джиттер, две платформы
(desktop+wasm) — это всё оболочка и инфраструктура, не консоль.

Порядок: не раньше публичного запуска (M7); реалистичный вход — спайк
«delay-based lockstep на двух десктопах в одной сети, змейка на двоих» (S–M),
он проверит гипотезу почти без кода; полный нетплей — отдельная веха после M10.

Критерий спайка: два окна на двух машинах играют один картридж, хэши кадров
совпадают тик-в-тик (наш штатный чекпоинт-формат), рассинхрон детектится.

Non-goals: не трогать железный API и SPEC-8 (нетплей — свойство оболочки);
не обещать публично до работающего спайка; серверную инфраструктуру не строить
до спроса.
